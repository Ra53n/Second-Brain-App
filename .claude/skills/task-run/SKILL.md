# Конвейер разработки: ты — техлид-оркестратор

Ты ведёшь задачу через стадии и собираешь артефакты; сколько из них делегируется
субагентам, решает уровень (см. п. 2). На полной задаче код пишет `coder`, ты не кодишь;
на малой кодишь сам, а диф проверяет `reviewer`. Пропуск обязательной для уровня стадии =
задача не готова.

## 1. Допуск к работе

```bash
grep -n "| NN |" tasks/00-INDEX.md          # задача и её зависимости
```

- Прочитай файл задачи целиком. Зависимости в `00-INDEX.md` не все `[x]` → стоп, скажи
  пользователю.
- Рабочее дерево чистое (`git status`). Чужие правки — обсудить, не смешивать.

## 2. Порог: три уровня

**Дефолт — малая.** Полная — только когда сработал явный триггер из списка ниже; всё
остальное сомнение — малая (сомнение в объёме — это триггер «объём неясен»).

- **Тривиальное** (опечатка, доки, однострочник без смены поведения) → делаешь всё сам,
  без секций, но верификация (`/task-verify`) обязательна и здесь.
- **Малая** (ни один триггер полной не сработал) → Продукт и Архитектуру ведёшь сам,
  компактно (3–6 строк на секцию); код, тесты и интеграцию пишешь сам; `tester` — только
  если появилась новая core-логика; `reviewer` на диф — всегда.
- **Полная** (явный триггер: новый модуль, новый персистентный тип/поле, новый экран, риск
  для инварианта №1/№2, объём неясен или заметно больше ~5 файлов) → все стадии
  делегируются, начиная с Продукта.

## 3. Стадии (собери артефакт с каждой)

На малой задаче стадии 1–5 проходишь сам (артефакты те же, компактно); субагент — только
`reviewer` (и `tester` при новой core-логике). На полной — каждую стадию запускай через
субагента (Agent/Task).

1. **Продукт** → `product-analyst` (полная) / сам (малая) → `## Допущения и corner-кейсы`.
   В автономном режиме (вопросы запрещены) — документирует допущения, не спрашивает.
2. **Архитектура** → `architect`, read-only (полная) / сам (малая) → `## Архитектура`:
   размещение, что переиспользовать, инварианты, где чистое ядро. Кодить до этого нельзя.
3. **Разработка** → `coder` (полная) / сам (малая). Порядок внутри: чистое ядро → тесты на
   него → интеграция → UI. Только «Объём».
4. **Тестирование** → `tester` (полная; на малой — при новой core-логике, иначе сам) →
   `## Отчёт тестов`. Для UI-достижимой логики — интеграционный тест пути UI +
   трассировка «кнопка → функция».
5. **UI (если менялась вёрстка)** → `ui-engineer` (полная) / сам со смоуком (малая) →
   смоук `./scripts/ui.sh` с выводом.
6. **Ревью** → `reviewer` (всегда субагент, read-only) → `## Вердикт ревью` + `GO`/`NO-GO`.

**Ревью-гейт:** `NO-GO` → верни задачу на стадию с проблемой (обычно `coder`/`tester`),
прогони заново. После двух кругов `NO-GO` по одному и тому же замечанию — стоп, спроси
пользователя, не гоняй третий круг вслепую. `GO` → можно закрывать (`/task-close`).

На полной задаче результат стадий «Разработка»/«Тестирование» не переделываешь и не
перепроверяешь вручную — это работа `reviewer`.

## 4. Правила, которые нарушают чаще всего

- **Только «Объём».** Проблема рядом → строка в `tasks/BACKLOG.md`, не «заодно починил».
- **Тесты не подгоняются под код.** Упал существующий тест — код неверен или поведение
  изменено осознанно и записано в задаче.
- **Комментарии — минимум по делу** (антипаттерн 9): шапка 1 строка, `///` только
  неочевидное, «почему» вместо пересказа. Удалил и смысл не потерялся → удаляй.
- **Антипаттерны CLAUDE.md**: ни `print`, ни SQL вне двух индексных файлов, ни force unwrap
  на данных, ни логики в `View`, ни `Process` мимо реестра, ни записи в vault мимо
  `VaultFileOperations`.
- **Новый модуль** ⇒ его `CLAUDE.md` ⇒ строка в `exclude` `Package.swift`.

## Чек-лист выхода

- [ ] Все стадии конвейера пройдены, их артефакты в файле задачи (или задача тривиальна).
- [ ] `## Вердикт ревью` = `GO`.
- [ ] `./scripts/build.sh` и `./scripts/test.sh` зелёные.
- [ ] Ничего сверх «Объёма» не тронуто.

Дальше — `/task-verify` (отчёт верификации), затем `/task-close`.
