# Ручные тесты чата тюнинга: baseline vs тюн

12 свежих фрагментов «встреч» для вкладки «Чат» раздела «Тюнинг». Ни один не взят из
train/valid и корпуса AMI — сочинены заново, поэтому сравнение честное. Половина —
в домене датасета (дизайн пульта), половина — чужие домены (проверка генерализации).

Как пользоваться: скопируйте фрагмент (только реплики, без заголовка и «Ожидаемого»),
отправьте в режиме «Базовая», затем тот же — в режиме «Тюн», сравните JSON и вердикт-чип.

---

## 1. Одно явное поручение, без срока (базовый случай) — корректный

```
Руководитель проекта: Так, по материалам корпуса мы определились — пластик, софт-тач.
Промышленный дизайнер: Да, я тогда возьму на себя подбор поставщиков покрытия.
Руководитель проекта: Отлично, договорились.
Маркетолог: А цвет обсудим на следующей встрече.
```

Ожидаемо: один item — Промышленный дизайнер / подбор поставщиков покрытия / due null.

## 2. Поручение с дословным сроком — корректный

```
Тимлид: Ребята, у нас релиз горит.
Аналитик: Я понял. Соберу воронку по онбордингу и пришлю до конца среды.
Тимлид: Хорошо, до среды жду.
Тестировщик: А я пока не буду ничего трогать на стейдже.
```

Ожидаемо: Аналитик / собрать воронку по онбордингу / «до конца среды». Ловушка: фраза
тестировщика — не поручение.

## 3. Несколько поручений разным людям — корректный

```
Руководитель проекта: Подводим итоги. Дизайнер интерфейса готовит три варианта раскладки кнопок.
Дизайнер интерфейса: Принято.
Руководитель проекта: Маркетолог — опрос по целевой аудитории, восемнадцать-тридцать пять.
Маркетолог: Сделаю.
Руководитель проекта: Я сам сведу бюджет и покажу финансистам.
```

Ожидаемо: три item'а, включая «Руководитель проекта / свести бюджет и показать финансистам».

## 4. Пусто: только мнения, ни одного решения — пограничный

```
Маркетолог: Мне кажется, скроллер удобнее кнопок.
Промышленный дизайнер: Ну, спорно, у скроллера износ выше.
Маркетолог: Зато молодёжи нравится.
Дизайнер интерфейса: А по цене они примерно одинаковые выходят.
Промышленный дизайнер: Вот именно, поэтому я бы не спешил.
```

Ожидаемо: `{"action_items": []}`. Частая ошибка baseline — «выудить» поручение из мнений.

## 5. Пусто-ловушка: идеи в сослагательном наклонении — пограничный

```
Тимлид: Можно было бы вынести настройки в отдельный экран.
Аналитик: Или вообще спрятать под жест, стоит подумать.
Тимлид: Да, надо бы как-нибудь прикинуть варианты.
Аналитик: Ага, вернёмся к этому позже.
```

Ожидаемо: `[]` — «можно было бы», «стоит подумать», «как-нибудь» — не договорённости.

## 6. Коллективное поручение → assignee null — корректный

```
Руководитель проекта: Значит, решено: к следующей встрече каждый приносит по три референса пультов конкурентов.
Маркетолог: Окей.
Промышленный дизайнер: Принял.
```

Ожидаемо: один item — assignee null (поручено всем) / принести по три референса /
«к следующей встрече».

## 7. Исполнитель не назван — корректный

```
Аналитик: Смотрите, без нагрузочного теста нас в прод не пустят.
Тимлид: Согласен. Тогда фиксируем: нагрузочный тест должен быть готов перед ревью.
Аналитик: Да, записал в протокол.
```

Ожидаемо: item с assignee null / подготовить нагрузочный тест / due null (или «перед
ревью» — спорно, интересно сравнить, вытащит ли модель это как срок).

## 8. Условное обещание — пограничный

```
Дизайнер интерфейса: Если успею до пятницы, посмотрю ещё анимации переходов.
Руководитель проекта: Ну, если успеешь — хорошо, но это не приоритет.
Дизайнер интерфейса: Понял.
```

Ожидаемо (строго): `[]` — обещание условное, приоритет снят. Мягкая трактовка с item —
тоже осмысленна; главное сравнить, одинаково ли ведут себя baseline и тюн.

## 9. Просьба отклонена — не поручение — пограничный

```
Маркетолог: Может, добавим голосовое управление в эту версию?
Руководитель проекта: Нет, в этот релиз точно не берём, бюджет не резиновый.
Маркетолог: Ладно, снимаю вопрос.
```

Ожидаемо: `[]`.

## 10. Шумный: перебивки и отступления, поручение спрятано внутри — сложный/шумный

```
Промышленный дизайнер: Эм, ну, короче, я вчера смотрел этот, как его,
Маркетолог: Угу.
Промышленный дизайнер: каталог компонентов, и там, ну, есть варианты.
Руководитель проекта: Кстати, кто-нибудь видел мой кабель от проектора?
Маркетолог: Ха, нет.
Руководитель проекта: Ладно. Так, по делу: маркетолог, подготовь к понедельнику сравнение цен из этого каталога.
Маркетолог: Эм, окей, к понедельнику сделаю.
Промышленный дизайнер: Ну вот, а я пока ничего, посмотрю ещё.
```

Ожидаемо: один item — Маркетолог / подготовить сравнение цен из каталога / «к понедельнику».

## 11. Чужой домен: ретро после инцидента — сложный/шумный

```
Дежурный инженер: База легла из-за миграции, откатили за двадцать минут.
Тимлид: Так. Дежурный инженер пишет постмортем к четвергу.
Дежурный инженер: Принято.
Тимлид: И отдельно: надо добавить алерт на репликационный лаг.
Дежурный инженер: Это я тоже могу взять.
Тимлид: Хорошо, бери.
```

Ожидаемо: два item'а на Дежурного инженера — постмортем / «к четвергу»; алерт на
репликационный лаг / due null.

## 12. Ловушка на выдуманный срок: срок звучит, но для другой задачи — пограничный

```
Руководитель проекта: Презентация для заказчика нужна к пятнице, я сам её соберу.
Промышленный дизайнер: Окей. А я тогда займусь макетом корпуса.
Руководитель проекта: Да, макет без спешки, дедлайна нет.
```

Ожидаемо: два item'а — Руководитель проекта / собрать презентацию / «к пятнице»;
Промышленный дизайнер / заняться макетом корпуса / **due null** (частая галлюцинация —
приклеить «к пятнице» и макету).

---

## На что смотреть при сравнении

1. Формат: baseline на непривычных доменах (2, 11) иногда отвечает не-JSON или с прозой —
   тюн должен держать строгий формат везде.
2. Пустые (4, 5, 9): не выдумывает ли модель поручения из мнений и отклонённых идей.
   Датасет учил «половиной пустых» именно этому.
3. Сроки (7, 12): берётся ли due только дословно и к своей задаче.
4. Вердикт-чип: расхождение redundancy (partial/disagree) чаще у baseline; scoring/self-check
   сигналы сравнивайте по раскрытому чипу.
5. Пограничный 8: интересно не «кто прав», а стала ли модель после тюна последовательнее.

---

## Как снять замеры для домашки

Прогоните все 12 фрагментов дважды: сначала в режиме «Базовая», затем в режиме «Тюн»
(перед сменой варианта нажмите «Очистить чат» — иначе замеры baseline и тюна смешаются
в одной статистике). Панель «Статистика сессии» под списком сообщений после каждого
прогона даёт нужные для отчёта числа: сколько отклонено (FAIL), сколько потребовало
повторного инференса и сколько доп. вызовов всего, влияние на latency (средняя основная
vs полная, наценка ×N) и на cost (токены prompt+completion; локальный прогон — $0, поэтому
cost выражается токенами и временем, не деньгами).

Чтобы увидеть влияние самого пайплайна уверенности (не модели), а не сравнить baseline
и тюн:

1. Оставьте включённым только тумблер «Проверки» (продовый дефолт), очистите чат, прогоните
   2–3 фрагмента — наценка latency в статистике будет ×1 (constraint не делает доп.
   вызовов, только разбирает уже полученный ответ).
2. Очистите чат, включите все четыре тумблера, прогоните те же 2–3 фрагмента — сравните
   наценку (должна вырасти, до 5 вызовов на сообщение) и вердикты (redundancy/scoring/
   self-check иногда понижают OK до UNSURE или FAIL там, где голого constraint было
   недостаточно).

Батч-прогон («Батч: базовая» / «Батч: тюн») тумблерам не подчиняется — он всегда гонит
полный пайплайн на 20 примерах `valid.jsonl`, это отдельное сравнение baseline/тюна,
не сравнение подходов пайплайна.
