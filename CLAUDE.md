# Second Brain — правила проекта

macOS-приложение «второй мозг»: аналог Obsidian с записью встреч, транскрипцией через
выбираемые LLM (локальные и облачные), чатом по базе знаний (RAG), MCP-интеграциями
(Jira, Confluence) и git-синхронизацией vault. Swift/SwiftUI, ~28 тыс. строк, 1000+ тестов.

**Этот файл — правила и процесс: как писать, как проверять, что запрещено.** Он главный;
при расхождении с другими документами прав он.

## Стек

| Слой | Выбор | Почему |
|---|---|---|
| Язык/UI | Swift 5.9+, SwiftUI (+AppKit для системного) | macOS-only; нужен нативный доступ к аудио, процессам, Keychain |
| Сборка | SPM-only executable, без .xcodeproj | `swift build` из CLI; `.app` собирает `run.sh` |
| Минимальная ОС | macOS 14+ | Core Audio process tap для системного звука (14.4+) |
| Заметки | обычные .md на диске, Obsidian-совместимо | данные переживут приложение |
| Индексы | SQLite: FTS5 (поиск) + таблица векторов (RAG) | системный libsqlite3, без зависимостей; всегда пересоздаваемы |
| Локальный LLM | Ollama как управляемый child-процесс | меньше своего кода, проверено в Manager Assistant |
| Локальная транскрипция | WhisperKit (CoreML), in-process | лучший Whisper на Apple Silicon |
| Облако | OpenAI, Gemini, Deepgram, AssemblyAI, OpenRouter, DeepSeek | за единой абстракцией провайдеров |
| Git | обёртка над git CLI через `Process` | без libgit2; auth — системный credential helper или SSH |
| Зависимости | ровно две: MarkdownUI, WhisperKit | каждая новая зависимость обсуждается с владельцем |

## Архитектура в десяти строках

`AppModel` — корень объектного графа, владелец менеджеров и сторов; связки «настройка ↔
поведение» держит он (Combine). UI — `NavigationSplitView` с разделами (заметки, поиск,
встречи, чат, пайплайны). У каждой области один `@MainActor ViewModel` — единственный
владелец мутабельного состояния; View только читают. Внешние сервисы спрятаны за
протоколами (`ChatProvider`, `TranscriptionProvider`, `EmbeddingProvider`), выбор
конкретного — за `FunctionRouter` (функция → провайдер → модель). Долгие процессы — FSM с
персистентным контекстом (встреча, прогон агента, пайплайн). Инструменты LLM (встроенные +
MCP) сводятся в один набор в `ChatToolAssembly` и проходят через слой разрешений.
Детали и потоки данных — [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

### Инвариант №1: vault — источник истины

Приложение работает поверх живой папки пользователя (возможно, его рабочего Obsidian
vault). Никакая операция не теряет и молча не перезаписывает .md. Все производные данные
(FTS-индекс, векторы, кэши) лежат **вне** vault — в
`~/Library/Application Support/SecondBrain/<vault-id>/` — и пересоздаваемы: удаление
индекса не должно стоить пользователю ничего, кроме времени переиндексации.

### Инвариант №2: жизненный цикл фоновых процессов

Любой запущенный приложением процесс регистрируется в `BackgroundProcessRegistry`,
поднимается лениво, гасится по idle-таймауту и **гарантированно** убивается в
`applicationWillTerminate` (SIGTERM → 3 с → SIGKILL). Чужой, не нами запущенный сервер
не гасится никогда.

## Паттерны, которые используем

**P1. Чистое ядро + тонкий оркестратор.** Решающая логика — в чистую функцию или `enum`
без I/O; оркестратор только гоняет сеть/диск/LLM и персистит. Чистое ядро тестируется
исчерпывающе и без моков. Эталоны: `AgentPhaseReducer` (все переходы FSM чата),
`MeetingFSM.transitions`, `PipelineScheduling`, `MeetingFolderPicker`, `VaultPath`,
`ToolRiskClassifier`.

**P2. Store.** Codable→JSON в Application Support, запись `.atomic`; битый файл уезжает в
`*.corrupt.json` и приложение стартует с пустого; автосохранение — debounce 300 мс на
`@Published`; снисходительный `init(from:)` (`decodeIfPresent` + дефолт) и **тест миграции
на каждое новое поле**. Эталоны: `ChatPersistence`, `SettingsStore`, `MeetingStore`.

**P3. Протокол → реестр → исполнитель.** Новая сущность добавляется файлом и строкой
регистрации, вызывающий код не меняется. `BuiltinTool` → `ToolRegistry` → `ToolExecutor`;
`ChatProvider`/`TranscriptionProvider` → `ProviderRegistry` → `FunctionRouter`.

**P4. Actor на разделяемый ресурс.** Всё, к чему могут обратиться параллельно, живёт в
`actor`: `GitClient` (FIFO-очередь — параллельные git портят `index.lock`), `MCPManager`,
`ToolExecutor`, `FileOpsContext`, индексные сервисы.

**P5. Crash-safety долгих процессов.** `persistNow()` синхронно после каждого перехода
FSM; на старте зависшие `running` → `paused`; resume идемпотентен (повтор шага безопасен);
гонки закрываются поколением (`agentGen`, `pipelineGen`) — сверка после каждого `await`.
Эталоны: `MeetingPipeline`, `ChatViewModel+AgentRun`, `PipelineEngine`.

**P6. Ошибка доходит до человека.** Своя `enum *Error: LocalizedError` на подсистему с
текстом, пригодным для показа в UI. Для инструментов LLM ошибка — это результат с текстом
`ERROR: …`, модель на него реагирует. Молча проглотить ошибку нельзя.

## Антипаттерны: запрещено

Каждый пункт проверяем grep'ом, и сейчас проект им соответствует — не сломай.

1. **`print()` / `NSLog()` для диагностики.** Сейчас в `Sources/` ноль вхождений. Ошибка
   идёт в `enum *Error` и доводится до UI, а не в консоль.
2. **SQL и `sqlite3_*` вне двух файлов** — [RAG/RagIndex.swift](Sources/SecondBrain/RAG/RagIndex.swift)
   и [Search/SearchIndex.swift](Sources/SecondBrain/Search/SearchIndex.swift). Никаких
   запросов из ViewModel, View или сервисов: им нужен метод индекса, а не строка SQL.
3. **Сеть в тестах.** Только фикстуры (`Tests/SecondBrainTests/Fixtures`), моки
   (`MockProviders`, `HashingEmbedder`) и инжектируемый транспорт (`GitHubClient`).
   Тест, который ходит в интернет, красный в самолёте — значит, бесполезный.
4. **Force unwrap на рантайм-данных.** `try!` и `!` допустимы ТОЛЬКО для компайл-тайм
   констант: статические `NSRegularExpression` и литеральные `URL(string:)` — так сейчас
   и есть. Данные от модели, сети, диска и пользователя — через `guard`/`throw`.
5. **Логика в `View`.** SwiftUI-структура читает состояние и вызывает методы ViewModel.
   Мутабельное состояние, I/O, разбор строк, обращения к диску в `body` — запрещено.
6. **`Process` мимо `BackgroundProcessRegistry`** и секреты в коде, логах, git-URL.
   Ключи живут в Keychain (fallback — env) и не показываются в UI никогда, даже частично.
7. **Запись в vault мимо `VaultFileOperations`** и mtime-guard `FileOpsContext`;
   производные данные (индексы, кэши, БД) внутри vault. См. инвариант №1.
8. **Правка файлов вне «Объёма» текущей задачи.** Заметил проблему рядом — запиши в
   `tasks/BACKLOG.md`, не чини по дороге.
9. **Комментарий-пересказ кода.** Комментарий обязан добавлять то, чего в коде нет («почему»,
   неочевидная оговорка). Пересказ следующей строки, `///` на самоочевидном члене,
   многострочная шапка с перечислением типов — вода: удалить. Ориентир — ~10–15% строк-
   комментариев, не 40%.

## Шаблоны

### Файл модуля

```swift
// ИмяФайла.swift — одна строка о назначении (задача NN).
// Важно: ≤2 строки ТОЛЬКО на неочевидную оговорку, которую из кода не вывести (иначе — нет).

import Foundation

struct Thing: Equatable {
    let id: String
}

enum ThingLogic {
    /// nil — когда вход не резолвится (единственное неочевидное в сигнатуре).
    static func compute(_ input: String) -> Thing? { ... }
}

enum ThingError: LocalizedError, Equatable {
    case notFound(String)

    var errorDescription: String? {
        switch self {
        case .notFound(let name): return "«\(name)» не найдено"
        }
    }
}
```

Порядок: заголовок → `import` → доменные типы → основной тип → `extension` → ошибки.
Комментарии — минимум по делу: шапка 1 строка, `///` только где имя+сигнатура не объясняют
сами, инлайн — только «почему». Удалил комментарий и смысл не потерялся → удаляй.

## Флоу работы с любой входящей задачей

Задача приходит как одна фраза пользователя, пункт бэклога или файл в `tasks/`. Кодить
начинаем только после Ф2. Фазы = стадии конвейера (см. «Конвейер разработки»): для полной
задачи техлид делегирует их субагентам `product-analyst`/`architect`; для малой — проходит
Ф1/Ф2 сам, компактно, без спавна субагентов (см. таблицу уровней).

**Ф1. Интервью — стадия `product-analyst` (полная) или техлид сам (малая).** Веди себя как
senior/staff-инженер, которому принесли запрос: пока не поймёшь сценарий и границы, не
проектируй. Обязательный чек-лист вопросов пользователю (в автономном режиме, когда вопросы
запрещены, — ответы на них документируются как допущения в `## Допущения и corner-кейсы`, не
спрашиваются; на малой задаче в интерактивном режиме техлид может задать их сам через
`AskUserQuestion`, без промежуточного субагента):

- Кто и в каком сценарии этим пользуется, что происходит непосредственно до и после?
- Пустой ввод, битый ввод, огромный ввод — что должно произойти?
- Нет сети, нет ключа, не скачана модель, нет прав (микрофон, папка) — как ведём себя?
- Краш или выход посреди операции — что пользователь увидит после перезапуска?
- Два одновременных запуска (два окна, пайплайн + руки) — что выигрывает?
- Уже сохранённые данные и настройки — нужна ли миграция, что со старыми файлами?
- Что явно НЕ надо делать в этой задаче?
- Как ты сам проверишь, что готово?

Спрашивай пачкой, а не по одному. Неочевидные ответы дословно уходят в файл задачи —
следующий агент не станет переспрашивать. На малой задаче чек-лист не обязательно расписывать
подробно — достаточно закрыть пункты, которые реально применимы, в 3–6 строках.

**Ф2. Архитектурный разбор — стадия `architect` (полная) или техлид сам (малая)** (артефакт
`## Архитектура`). Наложи задачу на существующую систему:

- в какой модуль ложится и почему именно туда;
- **что уже есть и переиспользуется** — обязательный поиск по коду до создания нового
  файла (половина «новых» задач закрывается существующим типом);
- какие инварианты затрагиваются (vault, фоновые процессы, персистентность);
- где чистое ядро (P1), где оркестратор, что персистится и как мигрирует (P2);
- какие существующие тесты придётся изменить — если много, вероятно, решение неверное;
- есть ли готовый аналог в Manager Assistant (таблица в CONVENTIONS.md) — актуально, только
  если задача создаёт подсистему с нуля (FSM, персистентность, RAG, MCP, LLM-клиент и т.п.).

На малой задаче — то же самое, но 3–6 строк по существу, без полного 8-пунктового отчёта.

**Ф3. Оформление.** Файл `tasks/NN-slug.md` по шаблону + строка в `00-INDEX.md`; если
задача выросла из бэклога — пункт там помечается `→ NN`.

**Ф4. Реализация — стадия `coder`.** Порядок: чистое ядро → тесты на него → интеграция →
UI. Только то, что в «Объёме». Комментарии — по ходу, минимум по делу (см. антипаттерн 9).

**Ф5. Проверка — стадии `tester` (+`ui-engineer`), затем `reviewer`.** `./scripts/build.sh`
и `./scripts/test.sh` зелёные (`tester` → `## Отчёт тестов`); критерии приёмки проходятся по
пунктам с доказательствами; UI-достижимое поведение — интеграционный тест пути + трассировка,
UI-вёрстка — смоук `./scripts/ui.sh` (`ui-engineer`); `reviewer` даёт `## Вердикт ревью` с
`GO`/`NO-GO`; `git grep -I --cached -e 'sk-' -e 'ghp_' -e 'AIza'` пусто. Итог — отчёт
верификации (жёсткое правило «Готовность = проверено»).

**Ф6. Закрытие** (только после `GO`). `## Результат` в файле задачи (что сделано, отклонения
от плана, что важно знать следующим агентам), чекбокс в `00-INDEX.md`, обновление
ARCHITECTURE.md при смене архитектурного решения, коммит с осмысленным сообщением.

## Конвейер разработки

Задача проходит один из трёх уровней конвейера — размер и риск решают, сколько стадий
делегируется субагентам, а не берутся ли стадии вообще. **Главный агент — техлид: он
оркестрирует и на не-тривиальной задаче код сам не пишет** — его пишет `coder`. Разница
уровней в другом: на полной задаче техлид делегирует и Продукт с Архитектурой (субагентам
`product-analyst`/`architect`), на малой — ведёт их сам, компактно (см. таблицу). Пропуск
обязательной для уровня стадии виден в диффе: у каждой — артефакт-секция в файле задачи, без
неё задача не готова.

| Уровень | Критерий | Продукт + Архитектура | Разработка → Ревью |
|---|---|---|---|
| Тривиальная | опечатка, правка доков, однострочник без смены поведения | техлид сам, без секций | solo, но `/task-verify` обязателен |
| **Малая** | техлид уверенно называет: один модуль, без нового персистентного типа/поля, без нового экрана, не задевает инварианты №1/№2 | техлид сам, компактно (3–6 строк на секцию, без спавна `product-analyst`/`architect`) | `coder → tester → (ui-engineer, если тронут UI) → reviewer` — как на полной |
| Полная | новый тип/поведение/модуль, риск для инварианта, объём неясен или велик | `product-analyst` → `architect`, полные субагенты | `coder → tester → (ui-engineer) → reviewer` |

Не уверен, к какому уровню отнести задачу — считай полной: это откат к более дорогому, но
безопасному варианту, а не наоборот.

| Стадия | Субагент | Обязательный артефакт |
|---|---|---|
| Продукт | `product-analyst` (полная) / техлид (малая) | `## Допущения и corner-кейсы` |
| Архитектура | `architect` (полная) / техлид (малая) | `## Архитектура` |
| Разработка | `coder` | код (дифф) |
| Тестирование | `tester` | `## Отчёт тестов` (что покрыто, найденные дыры, итог `./scripts/test.sh`) |
| UI (если есть) | `ui-engineer` | смоук-вывод `./scripts/ui.sh` |
| Ревью | `reviewer` | `## Вердикт ревью` (блокирующие / важные / мелочи + **GO / NO-GO**) |

- **Ревью-гейт:** без вердикта `GO` от `reviewer` коммита нет. NO-GO → техлид возвращает
  задачу на стадию с проблемой. После двух кругов `NO-GO` по одному и тому же замечанию —
  стоп, вопрос пользователю, а не третий круг вслепую.
- **Результат стадии техлид не переделывает и не перепроверяет вручную** — проверяет
  `reviewer` как отдельная стадия (это касается стадий `coder`/`tester`/`reviewer`; Продукт и
  Архитектуру на малой задаче техлид и так делает сам).
- Стадии `architect` и `reviewer` — read-only, ничего не пишут в код.
- `coder`/`tester`/`reviewer` делегируются на обоих не-тривиальных уровнях: независимость
  исполнителя от проверяющего важна и стоит дёшево (эти агенты и так самые узкие по контексту)
  — урезается только план и разбор архитектуры, где техлид может переиспользовать то, что уже
  понял сам, вместо того чтобы субагент заново собирал контекст с нуля.

## Жёсткие правила

- **Одна сессия — одна задача.** Возьми задачу из `tasks/`, проверь по `00-INDEX.md`, что
  её зависимости выполнены (нет — остановись и скажи пользователю), прочитай файл целиком,
  сделай только её. Нет подходящей задачи — она заводится из `BACKLOG.md` через `/task-new`.
- **Не-тривиальная задача идёт через конвейер ролей** (см. «Конвейер разработки», три
  уровня): техлид делегирует `coder`/`tester`/`reviewer` и сам не кодит; на малой задаче
  Продукт и Архитектуру ведёт сам, на полной — тоже делегирует. Каждая стадия оставляет
  артефакт в файле задачи; без вердикта `GO` от `reviewer` коммита нет. Solo целиком —
  только тривиальное.
- **Готовность = проверено и доказано.** Правка кода не завершена, пока не прогнаны
  `./scripts/build.sh` и `./scripts/test.sh` и их результат не приведён. «Должно работать» —
  не доказательство. Каждый code-таск заканчивается **отчётом верификации** (3–5 строк:
  собрано; N тестов; как проверено поведение — с доказательством).
- **Верификация обязательна, если правка затрагивает поведение или данные пользователя** —
  даже когда ни один `*View` не изменён. «Вёрстка не тронута» — не освобождение. Для
  UI-достижимой логики: интеграционный тест ровно того пути, что дёргает UI, + строка
  трассировки «диалог/кнопка → функция». Для чистой логики — интеграционный тест реального пути.
- **Секреты** никогда не попадают в код и git. Keychain, fallback — env.
- **Vault пользователя — источник истины.** Не терять, не перезаписывать молча.
- **Фоновые процессы** регистрируются и гасятся при `applicationWillTerminate`.
- **Тесты обязательны**: задача не выполнена без тестов на новую core-логику.
- **UI проверяется только через `./scripts/ui.sh`** (Accessibility с таймаутами):
  скриншоты окна невозможны в принципе — оно исключено из захвата экрана
  (`kCGWindowSharingState = 0`), снимок отдаёт обои. Ассерт `check` вместо чтения
  дерева; `dump` — только для разбора. Навигация — ссылкой
  `open "secondbrain://section/meetings"` (задача 50), а не кликом по сайдбару:
  AX-клик срабатывает через раз.
  Где результат виден в данных (`settings.json`, `chats.json`, SQLite) — проверяй там,
  это дешевле и надёжнее UI. Подробности — `/smoke-ui`.
- **После `install.sh` перезапусти приложение сам** (quit → open → проверь `pgrep`), не
  проси об этом пользователя.
- Реальный vault для ручных проверок — `/Users/kostyanikitin/Documents/Obsidian Vault/Second_Brain`:
  только чтение, ничего не ломать.
- Эталонный проект `/Users/kostyanikitin/Desktop/Manager assistant` — источник проверенных
  решений. Перед реализацией подсистемы с нуля проверь таблицу портирования в
  [CONVENTIONS.md](docs/CONVENTIONS.md).

## Сборка и тесты

```bash
./scripts/build.sh         # debug-сборка: только ошибки, уникальные варнинги, итог
./scripts/test.sh          # тесты: только падения и итоговая строка
./scripts/test.sh --filter ToolPermissionsTests   # один класс
swift run                  # запуск для разработки (без .app)
./run.sh                   # release + сборка SecondBrain.app
./install.sh               # run.sh + установка в /Applications
```

Скрипты сами выставляют `DEVELOPER_DIR` (тесты требуют полный Xcode, не Command Line
Tools) и пробрасывают аргументы в `swift build`/`swift test`. Голые `swift build` и
`swift test` — только когда нужен полный вывод для разбора конкретной проблемы.

## Экономия контекста

Контекст — расходуемый ресурс: чем меньше мусора в нём, тем точнее работа и дешевле
задача. Правила обязательны, не рекомендации.

1. **Сборка и тесты — только через `scripts/`.** `swift test` печатает по две строки на
   каждый из 1028 тестов; это десятки тысяч токенов ради одной строки «0 failures».
2. **Файлы-гиганты не читаются целиком.** Сначала `grep -n` по имени типа или метода,
   потом чтение нужного диапазона строк. Список тех, где это критично:
   `Chat/ChatViews.swift` (1212), `Editor/MarkdownEditorView.swift` (1036),
   `Chat/ChatViewModel.swift` (886), `Settings/SettingsViews.swift` (830),
   `Meetings/MeetingsPane.swift` (661), `GitSync/GitClient.swift` (594).
3. **`docs/ARCHITECTURE.md` (36 КБ) целиком не читается** — там сплошные абзацы по
   подсистемам. Нужен раздел — `grep -n "Пайплайны\|RAG\|Встреча" docs/ARCHITECTURE.md`
   и чтение диапазона. Специфика модуля обычно уже есть в его `CLAUDE.md`.
4. **Git — сводками**: `git diff --stat`, `git log --oneline -10`, `git show --stat`.
   Полный дифф — только по конкретному файлу и только когда он реально нужен.
5. **Не перечитывай файл после своей же правки** — редактор сообщил бы об ошибке.
6. **Субагент — на объёмную независимую работу.** Он заново собирает контекст, поэтому
   «прочитать три файла» дешевле сделать самому. Механические роли (`coder`, `tester`,
   `ui-engineer`) работают на sonnet, аналитические — на модели сессии.
7. **Корневой и модульные `CLAUDE.md` уже в контексте любого субагента** (кроме служебных
   Explore/Plan) — они подгружаются автоматически при старте. Не проси субагента прочитать
   их ещё раз через `Read`: это дублирует те же строки в контексте без всякой пользы.
8. **Ответ пользователю — 3–5 строк:** что сделано, что проверено, что требует решения.
   Без пересказа дифа, без таблиц ради таблиц, без повторения того, что видно в коммите.
   Подробности — по запросу.
