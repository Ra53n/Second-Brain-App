# Second Brain — правила проекта

macOS-приложение «второй мозг»: аналог Obsidian + запись встреч, транскрипция через
выбираемые LLM (локальные и облачные), чат по базе знаний (RAG), MCP-интеграции
(Jira, Confluence), git-синхронизация vault. Swift/SwiftUI, ~28 тыс. строк, 1000+ тестов.

**Этот файл — правила и процесс: как писать, как проверять, что запрещено.** Он главный;
при расхождении с другими документами прав он.

## Стек

| Слой | Выбор | Почему |
|---|---|---|
| Язык/UI | Swift 5.9+, SwiftUI (+AppKit для системного) | macOS-only; нативный доступ к аудио, процессам, Keychain |
| Сборка | SPM-only executable, без .xcodeproj | `swift build` из CLI; `.app` собирает `run.sh` |
| Минимальная ОС | macOS 14+ | Core Audio process tap для системного звука (14.4+) |
| Заметки | обычные .md на диске, Obsidian-совместимо | данные переживут приложение |
| Индексы | SQLite: FTS5 (поиск) + таблица векторов (RAG) | системный libsqlite3, без зависимостей; всегда пересоздаваемы |
| Локальный LLM | Ollama как управляемый child-процесс | меньше своего кода, проверено в Manager Assistant |
| Локальная транскрипция | WhisperKit (CoreML), in-process | лучший Whisper на Apple Silicon |
| Облако | OpenAI, Gemini, Deepgram, AssemblyAI, OpenRouter, DeepSeek | за единой абстракцией провайдеров |
| Git | обёртка над git CLI через `Process` | без libgit2; auth — системный credential helper или SSH |
| Зависимости | ровно две: MarkdownUI, WhisperKit | каждая новая — обсуждение с владельцем |

## Архитектура в десяти строках

`AppModel` — корень объектного графа, владелец менеджеров и сторов; связки «настройка ↔
поведение» держит он (Combine). UI — `NavigationSplitView` с разделами (заметки, поиск,
встречи, чат, пайплайны). У каждой области один `@MainActor ViewModel` — единственный
владелец мутабельного состояния; View только читают. Внешние сервисы — за протоколами
(`ChatProvider`, `TranscriptionProvider`, `EmbeddingProvider`), выбор конкретного — за
`FunctionRouter` (функция → провайдер → модель). Долгие процессы — FSM с персистентным
контекстом (встреча, прогон агента, пайплайн). Инструменты LLM (встроенные + MCP)
сводятся в один набор в `ChatToolAssembly` и проходят слой разрешений.
Детали и потоки данных — [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

### Инвариант №1: vault — источник истины

Приложение работает поверх живой папки пользователя (возможно, рабочего Obsidian vault).
Никакая операция не теряет и молча не перезаписывает .md. Производные данные (FTS-индекс,
векторы, кэши) — **вне** vault, в `~/Library/Application Support/SecondBrain/<vault-id>/`,
и пересоздаваемы: удаление индекса стоит пользователю только времени переиндексации.

### Инвариант №2: жизненный цикл фоновых процессов

Каждый запущенный приложением процесс регистрируется в `BackgroundProcessRegistry`,
поднимается лениво, гасится по idle-таймауту и **гарантированно** убивается в
`applicationWillTerminate` (SIGTERM → 3 с → SIGKILL). Чужой, не нами запущенный сервер
не гасится никогда.

## Паттерны, которые используем

**P1. Чистое ядро + тонкий оркестратор.** Решающая логика — чистая функция или `enum`
без I/O; оркестратор гоняет сеть/диск/LLM и персистит. Ядро тестируется исчерпывающе,
без моков. Эталоны: `AgentPhaseReducer` (все переходы FSM чата), `MeetingFSM.transitions`,
`PipelineScheduling`, `MeetingFolderPicker`, `VaultPath`, `ToolRiskClassifier`.

**P2. Store.** Codable→JSON в Application Support, запись `.atomic`; битый файл — в
`*.corrupt.json`, старт с пустого; автосохранение — debounce 300 мс на `@Published`;
снисходительный `init(from:)` (`decodeIfPresent` + дефолт) и **тест миграции на каждое
новое поле**. Эталоны: `ChatPersistence`, `SettingsStore`, `MeetingStore`.

**P3. Протокол → реестр → исполнитель.** Новая сущность — файл + строка регистрации,
вызывающий код не меняется. `BuiltinTool` → `ToolRegistry` → `ToolExecutor`;
`ChatProvider`/`TranscriptionProvider` → `ProviderRegistry` → `FunctionRouter`.

**P4. Actor на разделяемый ресурс.** Всё параллельно доступное живёт в `actor`:
`GitClient` (FIFO-очередь — параллельные git портят `index.lock`), `MCPManager`,
`ToolExecutor`, `FileOpsContext`, индексные сервисы.

**P5. Crash-safety долгих процессов.** `persistNow()` синхронно после каждого перехода
FSM; на старте зависшие `running` → `paused`; resume идемпотентен (повтор шага безопасен);
гонки закрыты поколением (`agentGen`, `pipelineGen`) — сверка после каждого `await`.
Эталоны: `MeetingPipeline`, `ChatViewModel+AgentRun`, `PipelineEngine`.

**P6. Ошибка доходит до человека.** Своя `enum *Error: LocalizedError` на подсистему,
текст пригоден для UI. Для инструментов LLM ошибка — результат с текстом `ERROR: …`,
модель на него реагирует. Молча проглотить ошибку нельзя.

## Антипаттерны: запрещено

Каждый пункт проверяем grep'ом; проект им соответствует — не сломай.

1. **`print()` / `NSLog()` для диагностики.** В `Sources/` ноль вхождений. Ошибка идёт в
   `enum *Error` и доводится до UI, не в консоль.
2. **SQL и `sqlite3_*` вне двух файлов** — [RAG/RagIndex.swift](Sources/SecondBrain/RAG/RagIndex.swift)
   и [Search/SearchIndex.swift](Sources/SecondBrain/Search/SearchIndex.swift). Никаких
   запросов из ViewModel, View, сервисов: им нужен метод индекса, не строка SQL.
3. **Сеть в тестах.** Только фикстуры (`Tests/SecondBrainTests/Fixtures`), моки
   (`MockProviders`, `HashingEmbedder`), инжектируемый транспорт (`GitHubClient`).
   Тест с интернетом красный в самолёте — бесполезный.
4. **Force unwrap на рантайм-данных.** `try!` и `!` — ТОЛЬКО компайл-тайм константы:
   статические `NSRegularExpression`, литеральные `URL(string:)`. Данные от модели, сети,
   диска, пользователя — через `guard`/`throw`.
5. **Логика в `View`.** SwiftUI-структура читает состояние и зовёт методы ViewModel.
   Мутабельное состояние, I/O, разбор строк, диск в `body` — запрещено.
6. **`Process` мимо `BackgroundProcessRegistry`** и секреты в коде, логах, git-URL.
   Ключи — в Keychain (fallback — env), в UI не показываются никогда, даже частично.
7. **Запись в vault мимо `VaultFileOperations`** и mtime-guard `FileOpsContext`;
   производные данные (индексы, кэши, БД) внутри vault. См. инвариант №1.
8. **Правка файлов вне «Объёма» текущей задачи.** Проблема рядом — строка в
   `tasks/BACKLOG.md`, не чинить по дороге.
9. **Комментарий-пересказ кода.** Комментарий добавляет то, чего в коде нет («почему»,
   неочевидная оговорка). Пересказ следующей строки, `///` на самоочевидном,
   многострочные шапки — вода: удалить. Ориентир ~10–15% строк-комментариев, не 40%.

## Флоу работы с любой входящей задачей

Задача приходит как фраза пользователя, пункт бэклога или файл в `tasks/`. Кодить — только
после Ф2. Кто ведёт фазы — решает уровень задачи (см. «Конвейер разработки»): на полной
Ф1/Ф2 делегируются `product-analyst`/`architect`, на малой техлид проходит их сам,
компактно (3–6 строк на секцию).

**Ф1. Интервью.** Работай как senior-инженер: не понял сценарий и границы — не проектируй.
Обязательный чек-лист corner-кейсов (пустой/битый/огромный ввод; нет
сети/ключа/модели/прав; краш посреди операции; два одновременных запуска; миграция уже
сохранённых данных; что явно НЕ делаем; как проверим готовность) — полный список вопросов
в скилле `/task-new`. Вопросы — пачкой, не по одному; в автономном режиме не задаются, а
документируются как допущения в `## Допущения и corner-кейсы`. Неочевидные ответы дословно
уходят в файл задачи — следующий агент не переспрашивает.

**Ф2. Архитектурный разбор** (артефакт `## Архитектура`). Наложи задачу на существующую
систему: в какой модуль ложится; **что уже есть и переиспользуется** (обязательный поиск
по коду — половина «новых» задач закрывается существующим типом); какие инварианты
затрагиваются; где чистое ядро (P1), что персистится и как мигрирует (P2); какие тесты
поедут (много — вероятно, решение неверное); есть ли аналог в Manager Assistant (только
для подсистем с нуля). Детали — в скилле `/task-plan`.

**Ф3. Оформление.** Файл `tasks/NN-slug.md` по шаблону + строка в `00-INDEX.md`; пункт
бэклога помечается `→ NN`.

**Ф4. Реализация.** Кто пишет код — по уровню: полная — `coder`, малая — техлид сам.
Порядок: чистое ядро → тесты на него → интеграция → UI. Только «Объём». Комментарии —
по ходу, минимум по делу (антипаттерн 9).

**Ф5. Проверка.** `./scripts/build.sh` и `./scripts/test.sh` зелёные (`## Отчёт тестов`);
критерии приёмки — по пунктам с доказательствами; UI-достижимое поведение —
интеграционный тест пути + трассировка, UI-вёрстка — смоук `./scripts/ui.sh`; `reviewer`
даёт `## Вердикт ревью` с `GO`/`NO-GO`; `git grep -I --cached -e 'sk-' -e 'ghp_' -e 'AIza'`
пусто. Итог — отчёт верификации (жёсткое правило «Готовность = проверено»).

**Ф6. Закрытие** (только после `GO`). `## Результат` в файле задачи (что сделано,
отклонения, что важно следующим агентам), чекбокс в `00-INDEX.md`, обновление
ARCHITECTURE.md при смене решения, коммит с осмысленным сообщением.

## Конвейер разработки

Уровень задачи решает, сколько стадий делегируется субагентам. **Дефолт — малая: техлид
делает работу сам, субагент только `reviewer`.** Полный конвейер — не «безопасный откат»,
а осознанный выбор для задач с явным триггером: каждый субагент заново собирает контекст,
на задачах без риска это чистые потери токенов. Пропуск обязательной для уровня стадии
виден в диффе: у каждой — артефакт-секция в файле задачи, без неё задача не готова.

| Уровень | Критерий | Кто делает |
|---|---|---|
| Тривиальная | опечатка, правка доков, однострочник без смены поведения | техлид solo, без секций; `/task-verify` обязателен |
| **Малая (дефолт)** | ни один триггер полной не сработал | техлид сам: Продукт и Архитектура компактно (3–6 строк на секцию), код, тесты и интеграция — сам; `tester` — только при новой core-логике; `reviewer` на диф — всегда |
| Полная | явный триггер: новый модуль, новый персистентный тип/поле, новый экран, риск для инварианта №1/№2, объём неясен или заметно больше ~5 файлов | полный конвейер: `product-analyst` → `architect` → `coder` → `tester` → (`ui-engineer`, если тронут UI) → `reviewer` |

Полная — только по явным триггерам из таблицы; сомнение в объёме — это триггер «объём
неясен», всё остальное сомнение — малая.

| Стадия | Кто (полная / малая) | Обязательный артефакт |
|---|---|---|
| Продукт | `product-analyst` / техлид | `## Допущения и corner-кейсы` |
| Архитектура | `architect` / техлид | `## Архитектура` |
| Разработка | `coder` / техлид | код (дифф) |
| Тестирование | `tester` / техлид (`tester` — при новой core-логике) | `## Отчёт тестов` (что покрыто, дыры, итог `./scripts/test.sh`) |
| UI (если есть) | `ui-engineer` / техлид со смоуком | смоук-вывод `./scripts/ui.sh` |
| Ревью | `reviewer` — всегда субагент, read-only | `## Вердикт ревью` (блокирующие / важные / мелочи + **GO / NO-GO**) |

- **Ревью-гейт (малая и полная):** без вердикта `GO` от `reviewer` коммита нет. NO-GO →
  вернуть задачу на стадию с проблемой. Два круга `NO-GO` по одному замечанию — стоп,
  вопрос пользователю, не третий круг вслепую.
- На полной задаче техлид код сам не пишет и результаты стадий вручную не перепроверяет —
  проверяет `reviewer`. Стадии `architect` и `reviewer` — read-only, в код не пишут.
- **После задачи/PR — цикл прогона по импакту** (`/smoke-cycle`, `scripts/smoke-all.sh`):
  затронутые код-тесты + смоук-сценарии выбираются по `smoke/impact-map.tsv`, единый отчёт
  с HTML и локализацией падения; под новую фичу дописывается смоук-сценарий. Уровни 1/2 —
  задачи 58/59, петля — 60.

### Сценарные профили

Рядом с ролями конвейера — три профиля под **форму задачи** (`.claude/agents/`, что делает
каждый — в его `description`): `research`, `bugfix`, `refactor`. `research` read-only и
терминальный: дифа не производит, гейт не нужен, к закрытию задач с диффом не применяется —
им можно ответить на архитектурный вопрос (Ф2), но он не заменяет стадию «Разработка».
`bugfix`/`refactor` встают на стадию «Разработка» вместо `coder` и **не коммитят** — дальше
как обычно: `tester`, `reviewer`, ревью-гейт, коммит за техлидом. Уровни действуют и здесь:
профили спавнятся на полном уровне, малый баг или точечный рефакторинг техлид делает сам
(малая: сам + `reviewer`).

Профиль выбирается по форме запроса, когда задача пришла устной фразой; когда задача уже
оформлена файлом `tasks/NN-slug.md`, профиль детерминирован полем `## Тип`:

| `## Тип` | Профиль (полная) | Малая (техлид сам) |
|---|---|---|
| баг | `bugfix` | методология bugfix соло: воспроизвести → причина → минимальная правка |
| рефакторинг | `refactor` | методология refactor соло: сверка с P1–P6, правка без смены поведения |
| фича / тест / документация | `coder` | техлид пишет сам |

Это единственное объективное сопоставление типа задачи и профиля — им пользуется
`/execution-loop`, чтобы не угадывать профиль по тексту на лету.

## Жёсткие правила

- **Одна сессия — одна задача.** Возьми задачу из `tasks/`, сверь зависимости по
  `00-INDEX.md` (не выполнены — стоп, скажи пользователю), прочитай файл целиком, сделай
  только её. Нет подходящей — заводится из `BACKLOG.md` через `/task-new`. Исключение —
  явный автономный режим `/execution-loop`: там сессия — очередь задач до исчерпания пула
  или стоп-условия (см. скилл `execution-loop`), а не одна задача.
- **Уровень задачи определяет конвейер** (см. «Конвейер разработки»): дефолт — малая
  (техлид сам, `reviewer` на диф обязателен), полная — только по явным триггерам, тогда
  все стадии через субагентов. Каждая стадия оставляет артефакт в файле задачи; без
  вердикта `GO` от `reviewer` коммита нет. Solo целиком — только тривиальное
  (`/task-verify` обязателен и там).
- **Готовность = проверено и доказано.** Правка не завершена, пока не прогнаны
  `./scripts/build.sh` и `./scripts/test.sh` и результат не приведён. «Должно работать» —
  не доказательство. Каждый code-таск заканчивается **отчётом верификации** (3–5 строк:
  собрано; N тестов; как проверено поведение — с доказательством).
- **Верификация обязательна, если правка затрагивает поведение или данные пользователя** —
  даже когда ни один `*View` не изменён. «Вёрстка не тронута» — не освобождение. Для
  UI-достижимой логики: интеграционный тест ровно того пути, что дёргает UI, + строка
  трассировки «диалог/кнопка → функция». Для чистой логики — интеграционный тест
  реального пути.
- **Секреты** никогда не попадают в код и git. Keychain, fallback — env.
- **Vault пользователя — источник истины.** Не терять, не перезаписывать молча.
- **Фоновые процессы** регистрируются и гасятся при `applicationWillTerminate`.
- **Тесты обязательны**: задача не выполнена без тестов на новую core-логику.
- **UI проверяется только через `./scripts/ui.sh`** (Accessibility с таймаутами):
  скриншоты окна невозможны в принципе — оно исключено из захвата экрана
  (`kCGWindowSharingState = 0`), снимок отдаёт обои. Ассерт `check` вместо чтения дерева;
  `dump` — только для разбора. Навигация — ссылкой `open "secondbrain://section/meetings"`
  (задача 50), не кликом по сайдбару: AX-клик срабатывает через раз. Где результат виден
  в данных (`settings.json`, `chats.json`, SQLite) — проверяй там, это дешевле и надёжнее
  UI. Подробности — `/smoke-ui`.
- **После правки/PR — прогон по импакту**: `./scripts/smoke-all.sh` по
  `smoke/impact-map.tsv` сам выбирает затронутые код-тесты и смоук-сценарии, даёт единый
  отчёт + HTML, при падении подсказывает место. Цикл целиком и дописывание сценариев —
  `/smoke-cycle`.
- **После `install.sh` перезапусти приложение сам** (quit → open → проверь `pgrep`), не
  проси пользователя.

## Сборка и тесты

```bash
./scripts/build.sh         # debug-сборка: только ошибки, уникальные варнинги, итог
./scripts/test.sh          # тесты: только падения и итоговая строка
./scripts/test.sh --filter ToolPermissionsTests   # один класс
swift run                  # запуск для разработки (без .app)
./run.sh                   # release + сборка SecondBrain.app
./install.sh               # run.sh + установка в /Applications
```

Скрипты сами выставляют `DEVELOPER_DIR` (тесты требуют полный Xcode, не Command Line
Tools) и пробрасывают аргументы в `swift build`/`swift test`. Голые `swift build` и
`swift test` — только когда нужен полный вывод для разбора конкретной проблемы.

## Экономия контекста

Контекст — расходуемый ресурс: меньше мусора — точнее работа и дешевле задача. Правила
обязательны, не рекомендации.

1. **Сборка и тесты — только через `scripts/`.** `swift test` печатает по две строки на
   каждый из 1028 тестов — десятки тысяч токенов ради строки «0 failures».
2. **Навигация по коду — `ast-index`, не grep + чтение файла целиком.** Установлен
   локально (`~/.local/bin/ast-index`), SQLite-индекс символов по репо:
   `ast-index symbol <Имя>` — определение; `ast-index outline <файл>` — структура файла;
   `ast-index usages <Имя>` / `ast-index callers <Имя>` — кто использует/зовёт. Возвращает
   точные срезы вместо целых файлов. После правок и смены ветки — `ast-index update`.
   Файл длиннее ~600 строк (`ChatViews`, `MarkdownEditorView`, `ChatViewModel`,
   `SettingsViews` и т.п.) не читается целиком никогда: сначала `outline`/`grep -n`,
   потом чтение нужного диапазона строк.
3. **`docs/ARCHITECTURE.md` (36 КБ) целиком не читается** — сплошные абзацы по
   подсистемам. Нужен раздел — `grep -n "Пайплайны\|RAG\|Встреча" docs/ARCHITECTURE.md`
   и чтение диапазона. Специфика модуля обычно уже в его `CLAUDE.md`.
4. **Git — сводками**: `git diff --stat`, `git log --oneline -10`, `git show --stat`.
   Полный дифф — только по конкретному файлу и только когда реально нужен.
5. **Не перечитывай файл после своей же правки** — редактор сообщил бы об ошибке.
6. **Субагент — на объёмную независимую работу.** Он заново собирает контекст: «прочитать
   три файла» дешевле сделать самому. Механические роли (`coder`, `tester`, `ui-engineer`)
   работают на sonnet, аналитические — на модели сессии.
7. **Корневой и модульные `CLAUDE.md` уже в контексте любого субагента** (кроме служебных
   Explore/Plan) — подгружаются автоматически при старте. Не проси субагента перечитать
   их через `Read` — дубль тех же строк без пользы.
8. **Ответ пользователю — 3–5 строк:** что сделано, что проверено, что требует решения.
   Без пересказа дифа, без таблиц ради таблиц, без повторения видного в коммите.
   Подробности — по запросу.
