# Задача 52: переименование заметки чинит ссылки на неё

## Цель

Пользователь переименовывает заметку в дереве vault (диалог «Новое имя»). Все
`[[ссылки]]` на неё из других заметок автоматически меняют цель на новое имя, не
ломаясь. Обычная форма, алиас, заголовок секции и путь-префикс сохраняются:

- `[[Старое]]` → `[[Новое]]`
- `[[Старое|как показывать]]` → `[[Новое|как показывать]]`
- `[[Старое#Раздел]]` → `[[Новое#Раздел]]`
- `[[папка/Старое]]` → `[[папка/Новое]]`

Это пункт 4 бэклога («Переименование заметки с обновлением ссылок»), под который
уже подготовлен `LinkIndex` (см. его заголовок: «Прицел на задачу 19… у каждой
ссылки хранится точный диапазон в исходном файле»).

## Зависимости

- 02 (CRUD vault, `VaultFileOperations.rename`) — выполнена;
- 04 (`WikilinkParser`, `LinkIndex`, `backlinks(to:)`, `resolve`) — выполнена;
- 03 (редактор, `checkExternalChange`) — выполнена, нужен для корректной
  реакции на внешнюю перезапись открытого файла.

## Объём

1. **Чистое ядро** — `Sources/SecondBrain/Links/WikilinkRename.swift`:
   `WikilinkRenamer.rewrite(content:targets:to:)` — по тексту заметки и множеству
   «целей, которые надо переписать» (нормализованные строки цели) возвращает новый
   текст и число замен. Только строковые операции, без I/O, покрыто тестами
   исчерпывающе.
2. **Оркестратор I/O** — там же, `LinkRenameApplier.apply(backlinks:to:)`:
   группирует вхождения по файлу-источнику, перечитывает каждый файл **свежим** с
   диска, зовёт чистое ядро, пишет назад атомарно. Возвращает список файлов, где
   запись/чтение не удались, — вызывающий доводит до `lastError`.
3. **Интеграция** — `VaultManager.rename(_:to:)`: до переименования собрать
   `backlinks(to: oldURL)` (по свежему индексу — `refresh()` перед сбором), после
   успешного переименования применить `LinkRenameApplier`, затем `refresh()` +
   `linkVersion += 1`. UI (диалог в `VaultViews`) не трогаем — точка вызова та же.
4. **Тесты** — `Tests/SecondBrainTests/LinkRenameTests.swift`: все формы ссылок,
   кириллица, пробелы в имени, код-блоки (не трогаем), коллизия имён (цель не в
   множестве — не переписываем), несколько ссылок в одном файле, ноль замен.
   Плюс интеграционный тест на temp-vault через `VaultManager`.

## Вне объёма (осознанные решения)

- **Переименование папки и перемещение заметки** (`move`) не чинят путь-ссылки
  `[[папка/Имя]]`. Это отдельный класс (меняется путь, а не базовое имя) и больший
  объём; заведён пунктом в `BACKLOG.md`. Здесь — только переименование `.md`-файла.
- **Embed `![[...]]`** — вне поддержки парсера (задача 04), сюда не входит.
- **Self-ссылки** (заметка ссылается сама на себя `[[Старое]]` внутри `Старое.md`)
  не переписываются: `backlinks(to:)` исключает файл-источник, равный цели. Редкий
  случай, поведение осознанное.
- **Несохранённые правки в редакторе.** Переписываем только то, что на диске.
  Если открытый файл имеет несохранённые правки, атомарная перезапись его на диске
  вызовет штатный конфликт `EditorViewModel.checkExternalChange` (инвариант №1 —
  решает пользователь), данные не теряются молча.
- **Имя с `#`, `|`, `[`, `]`** ломает синтаксис wikilink. `VaultFileOperations`
  запрещает `/`, пустое и ведущую точку, но не эти символы. Переписываем базовое
  имя дословно; если пользователь ввёл такое имя — ссылка может стать
  неоднозначной. Крайне редкий случай, отдельно не защищаемся.
- **Переименование в не-`.md`** (пользователь стёр расширение): файл покидает граф
  ссылок, чинить нечего — при `newURL.pathExtension != "md"` ссылки не трогаем.
- **Частичный сбой (краш между переименованием и правкой части файлов):** файл уже
  переименован, часть ссылок ещё не поправлена. На старте индекс перестроится,
  непоправленные ссылки останутся указывать на старое имя (как в Obsidian).
  Транзакционности нет — вне объёма.

## Ключевые проектные решения

- **Почему не берём готовые диапазоны из `LinkIndex`.** У вхождений в индексе есть
  точные `NSRange`, но они с момента индексации. Чтобы не порезать изменившийся с
  тех пор файл, ядро **перечитывает файл свежим и заново парсит** `WikilinkParser`,
  а из индекса берёт только *множество целевых строк*, которые резолвятся в
  переименованную заметку (через `backlinks`, где резолв Obsidian-совместимый).
- **Почему нужно множество целей, а не сравнение по базовому имени.** Коллизия
  имён: `[[Имя]]` (без пути) резолвится в файл с кратчайшим путём, `[[глубоко/Имя]]`
  — в другой. Если переименовать «глубокий», переписывать надо только ссылки,
  которые реально в него резолвятся, а не все с базовым именем «Имя».
- **Запись напрямую атомарно, а не через `VaultFileOperations`.** `VaultFileOperations`
  покрывает структурные операции (создать/переименовать/переместить/в корзину), а
  не правку содержимого. Правка содержимого существующего файла — как
  `EditorViewModel.saveNow` (тоже пишет `Data.write(options:.atomic)` напрямую).
  Инвариант №1 держится: перечитываем свежим прямо перед записью; открытый файл с
  несохранёнными правками защищён конфликтом редактора.

## Критерии приёмки

1. `swift build` и `swift test` зелёные.
2. Переименовал заметку, на которую ссылались из трёх других, — во всех трёх
   `[[Старое*]]` стали `[[Новое*]]` с сохранением алиасов/заголовков/путей
   (интеграционный тест на temp-vault + ручная проверка в собранном приложении).
3. Ссылка `[[Имя]]`, резолвящаяся в *другую* заметку с тем же базовым именем, при
   переименовании «нашей» не трогается (тест коллизии).
4. Ссылки внутри код-блоков не переписываются (тест).
5. Секретов в диффе нет; антипаттерны (`print`, SQL вне двух файлов, force-unwrap
   на рантайм-данных, логика во View) не внесены.

## Результат

Сделано по плану, отклонений нет.

**Что появилось:**
- `Sources/SecondBrain/Links/WikilinkRename.swift`:
  - `WikilinkRenamer.rewrite(content:targets:to:)` — чистое ядро (P1): парсит
    текст `WikilinkParser`'ом, переписывает справа налево только ссылки, чья цель
    (без регистра/внешних пробелов) входит в `targets`, меняя базовое имя;
    алиас/`#заголовок`/путь-префикс/внешние пробелы сохраняются дословно.
  - `LinkRenameApplier.apply(backlinks:to:)` — оркестратор I/O: собирает множество
    целей из `backlinks`, перечитывает каждый файл-источник свежим, зовёт ядро,
    пишет назад `Data.write(.atomic)`. Возвращает имена непрочитанных/незаписанных
    файлов.
- `VaultManager.rename(_:to:)`: для `.md`-файла собирает `backlinks(to: oldURL)` по
  свежему индексу ДО переименования, после успешного rename применяет
  `LinkRenameApplier`, обновляет индекс и `linkVersion`. UI не менялся — точка
  вызова из диалога `VaultViews` та же.
- Тесты `Tests/SecondBrainTests/LinkRenameTests.swift`: 7 юнит-тестов ядра
  (все формы, коллизия, код-блоки, кириллица, пробелы в имени, ноль замен,
  суперстрока) + 2 интеграционных на temp-vault (починка по всему vault; коллизия
  имён не задевает чужую заметку).

**Что важно знать следующим:**
- Диапазоны из `LinkIndex` для самой правки НЕ используются (могли устареть) —
  ядро заново парсит свежий файл; из индекса берётся только *множество целей*, где
  резолв Obsidian-совместимый и коллизии имён разрешаются верно.
- Запись содержимого идёт напрямую атомарно (как `EditorViewModel.saveNow`), а не
  через `VaultFileOperations` — тот отвечает за структурные операции, не за правку
  содержимого. Инвариант №1 держится: перечитываем свежим прямо перед записью;
  открытый файл с несохранёнными правками защищён штатным конфликтом редактора.
- Вне объёма (в `BACKLOG.md` п. 29): перемещение заметки и переименование/
  перемещение папки не чинят путь-ссылки `[[папка/Имя]]` — там меняется путь, а не
  базовое имя, механика та же, но по префиксу пути и каскадом по вложенным.

**Проверка:** `./scripts/build.sh` зелёный; `./scripts/test.sh` — 1044 теста,
0 падений (было ~1035, +9 новых); секретов и антипаттернов в диффе нет.
Поведение доказано на уровне данных — интеграционные тесты переименовывают файл на
реальном диске (`VaultFileOperations.rename` + `LinkRenameApplier.apply`) и сверяют
итоговое содержимое `.md`; UI-обвязка (диалог → `manager.rename`) не менялась.
