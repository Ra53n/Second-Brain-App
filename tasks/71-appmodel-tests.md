# Задача 71: тесты на `AppModel.swift`

## Тип

тест

## Модель

haiku

## Цель

`Sources/SecondBrain/App/AppModel.swift` (корень объектного графа — владелец менеджеров и
сторов, связки «настройка ↔ поведение») не упоминается ни в одном тестовом файле. Логика
инициализации/связывания сервисов не покрыта — регрессия в порядке инициализации или в
связке Combine-подписок останется незамеченной до ручного запуска приложения.

## Зависимости

Нет.

## Объём

1. Изучить `AppModel.swift`: что именно можно протестировать без реального UI-рантайма —
   порядок инициализации менеджеров, связки «настройка → поведение» (если они вынесены в
   проверяемую форму), поведение при отсутствии части конфигурации/ключей.
2. Написать `Tests/SecondBrainTests/AppModelTests.swift` на то, что реально тестируется без
   моков системных API (Core Audio, FS и т.п. — если `AppModel` их трогает напрямую в init,
   такие пути не покрываем, это честно фиксируется в отчёте, а не притягивается моками).

## Вне объёма

Рефакторинг `AppModel` ради тестируемости — только тестирование того, что уже тестируемо.
Если по факту тестируемой логики почти нет (всё I/O-инициализация), задача честно
завершается коротким отчётом «покрывать нечего без рефакторинга» — это тоже валидный исход.

## Критерии приёмки

- [x] `Tests/SecondBrainTests/AppModelTests.swift` существует и содержит хотя бы один
      содержательный тест (не заглушку), либо в файле задачи явно объяснено, почему
      покрытие невозможно без рефакторинга (см. «Вне объёма»).
- [x] `./scripts/build.sh` и `./scripts/test.sh` зелёные, число тестов не уменьшилось.

## Отчёт тестов

**Первая попытка (5 тестов, `testInitialization`, `testDotItemsSyncBidirectional`,
`testAutoBackupMinutesSyncBidirectional`, `testLocalIdleTimeoutPropagation`,
`testInitializationWithNoVaultRestored`) была ошибочной и удалена.** Все пять
конструировали реальный `AppModel()` напрямую. `AppModel.init()`
(`Sources/SecondBrain/App/AppModel.swift:44-93`) не имеет DI-точек: `SettingsStore()`,
`VaultManager(restoreLast:)`, `PipelineStore()` и остальные сторы/менеджеры создаются
внутри `init` без возможности подменить пути или транспорт — это реальные Application
Support файлы разработчика (`settings.json`, `pipelines.json`, `pipeline-runs.json`) и
`UserDefaults.standard`. При ревью эмпирически подтверждено: прогон тестового набора
необратимо изменил боевые `settings.json`/`pipelines.json` на машине разработчика —
ревьюер восстанавливал их вручную. Это прямое нарушение антипаттерна 3
(«ноль зависимости от машины разработчика», `Tests/SecondBrainTests/CLAUDE.md`).

Отдельно от порчи файлов: `wire()` (App/AppModel.swift:97) в конце безусловно вызывает
`pipelineScheduler.start()` и `prWatcher.start()` — каждый созданный в тесте `AppModel`
запускал реальный cron-подобный планировщик пайплайнов и PR-watcher поверх боевого
`PipelineStore`. При другом состоянии диска (сохранённый включённый pipeline с
GitHub-репозиторием) это означало бы реальный сетевой поллинг GitHub из юнит-теста —
антипаттерн 3 в чистом виде, и незакрываемые фоновые Task на весь прогон тестов.

**Проверка альтернативного пути (шаг 2 задания):** проверено, есть ли в проекте паттерн
«чистая функция связывания + тонкий вызов в init», применяемый где-то ещё в кодовой базе,
которым можно было бы протестировать `wire()` без полного `AppModel`. Такого паттерна в
проекте нет (`grep -rn "func wire" Sources/SecondBrain/` — только приватные методы
`AppModel` самого себя). Все связки Combine в `wire()` замкнуты на `let`-свойства,
инициализированные внутри того же `init()` реальными I/O-объектами
(`SettingsStore`, `VaultManager`, `PipelineStore`, ...): нет протокола, нет параметра
конструктора, через который можно подставить изолированные/фейковые издатели. Извлечь
`wire()` в свободную функцию с публишерами как параметрами — это рефакторинг
`AppModel` ради тестируемости, явно исключённый из объёма задачи («Вне объёма»).

**Итог: тестировать нечего без рефакторинга.** `AppModel.init()` — чистая
I/O-инициализация (создание сторов, менеджеров, вью-моделей) без ветвлений и без
чистого вычислительного ядра; `wire()` — Combine-подписки, неотделимые от реального
графа объектов, с побочным эффектом (безусловный запуск фоновых циклов). Единственный
безопасный способ покрыть эту логику тестами — добавить DI-конструктор `AppModel(...)`,
принимающий уже созданные сторы/менеджеры (или протоколы над ними), и вынести `wire()`
в форму, принимающую издатели явно — это прямой рефакторинг производственного кода,
запрещённый разделом «Вне объёма» данной задачи.

`Tests/SecondBrainTests/AppModelTests.swift` удалён.

## Результат

Валидный отрицательный исход: `AppModel.init()`/`wire()` нельзя протестировать без
DI-рефакторинга (вне объёма) — не имеет ни одной инжектируемой точки для сторов/менеджеров,
`wire()` безусловно стартует фоновые циклы. Первая попытка (5 тестов на реальном
`AppModel()`) была ошибочной и опасной — портила боевые Application Support файлы
разработчика и запускала неостанавливаемые фоновые Task; удалена на первом круге ревью.
`GO` со второго круга.

Следующим агентам: если появится задача добавить DI-конструктор `AppModel` (например, ради
именно этой тестируемости), тесты на `wire()`/инициализацию тогда станут возможны —
сейчас это прямо запрещённый для этой задачи рефакторинг.
