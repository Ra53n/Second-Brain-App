# Задача 39. Файловые инструменты агента + слой разрешений

## Цель

Ассистент в чате выполняет реальные операции над любым выбранным каталогом (репозиторий, произвольная папка, vault): читает и ищет по нескольким файлам, анализирует, создаёт/изменяет/удаляет файлы, запускает команды (сборка, тесты) — под управлением слоя разрешений как в Claude Code: операции классифицируются на безопасные/правки/опасные, режим работы выбирается per-чат, подтверждение даётся один раз или на сессию. Изменения сохраняются на диск, а diff по каждому файлу остаётся в истории чата (отчёт и воспроизводимость).

## Зависимости

21 (BuiltinTool/SafePath/ToolExecutor), 27 (чипы туллинга), 34 (реестр баз знаний), 35 (FSM + ChatToolAssembly).

## Объём работ

- [x] `Tools/UnifiedDiff.swift` — чистый построчный unified diff (LCS, hunks, «\ No newline», фолбэк для гигантских файлов). git не используется — diff работает для любых папок и новых файлов.
- [x] `Tools/ToolPermissions.swift` — уровни риска `ToolRiskLevel` (safe/write/dangerous), режимы `AgentPermissionMode` (ask/auto/autoDanger), чистый классификатор `ToolRiskClassifier` (встроенные инструменты, MCP `slug__tool` → write, allowlist команд run_command c разбором `&& ; | ||` и запретом редиректов/подстановок, «конфиг-пути» — скрытые файлы), матрица `ToolPermissionPolicy`, ключи операций для сессионного allowlist.
- [x] `Tools/FileTools.swift` — `search_files` (литеральный поиск, капы), `write_file` (кап 256 КБ, промежуточные папки), `edit_file` (old_string→new_string, replace_all), `delete_file` (в Корзину), `FileOpsContext` (actor per-чат: реестр чтений + накопитель изменений), `FileChangePreview` (diff-превью для карточки approve). Vault-safety: read-before-write + mtime-guard; обрезанное чтение не регистрируется.
- [x] `Tools/RunCommandTool.swift` — `run_command`: zsh -c в корне чата, таймаут (default 120 c, cap 600), объединённый вывод ≤32 КБ + exit code, регистрация процесса в `BackgroundProcessRegistry` (инвариант №2), SIGTERM→SIGKILL по таймауту.
- [x] `ReadFileTool` регистрирует полное чтение в `FileOpsContext`; `ToolContext`/`ToolExecutor` прокидывают контекст файловых операций.
- [x] Per-чат рабочий каталог: `ChatConfiguration.projectRootPath` (nil = глобальный `projectRepoPath`), per-root кэш в `ProjectToolsProvider.toolset(rootOverride:)`, мост `ProjectToolsBridge` с override во всех замыканиях.
- [x] Approve-гейт: `ChatToolAssembly.assembleTooling` классифицирует каждый вызов (project и MCP), при необходимости ждёт решения на `CheckedContinuation` (`Chat/ToolApprovalCenter.swift`); «Разрешить» / «На сессию» (in-memory ключи до перезапуска) / «Отклонить» (модели уходит `ERROR:`); отмена хода/паузы FSM гасит ожидание. Лимит итераций одиночного хода с project-инструментами 6 → 10.
- [x] Отчёт по файлам: `ChatMessage.fileChanges` (`FileChangeDisplay`: путь, вид операции, diff ≤32 КБ) — цепляется к сообщению хода и к сообщениям фаз FSM; рендер — `FileChangesBlock` (раскрашенный diff) в MessageBubble.
- [x] UI: карточка `ToolApprovalCard` над полем ввода; поповер чипа «Проект» — каталог этого чата (NSOpenPanel), «Вернуть глобальный», сегмент-пикер режима с предупреждением для «Авто-опасного», кнопка «Сделать базой знаний» (реюз `KnowledgeBaseStore.addFolder` + включение базы в чате); чип показывает «Проект (чат)» и режим.
- [x] Промпт: `ChatPromptBuilder.fileToolsDirective(mode:rootPath:)` — в системный промпт одиночного хода и FSM-фаз (отказ пользователя — не сбой).
- [x] MCP: шаблон `MCPServer.filesystemTemplate` + кнопка в настройках — внешняя альтернатива встроенным инструментам.
- [x] Закрыты пп. 10 (подтверждение MCP-вызовов) и 16 (подтверждение write-инструментов) бэклога.

## Результат

Выполнено 2026-07-18. 933 теста зелёные.

Что сделано — по объёму работ выше, всё вошло. Ключевые решения и отклонения:

- **Approve через паузу tool-цикла**, а не стейджинг правок: правка применяется в момент «Разрешить», инструмент получает реальный результат, модель всегда видит настоящее состояние диска (никаких оверлеев непримененных правок). Ожидание — `CheckedContinuation` в `ToolApprovalCenter`; провайдерских таймаутов между итерациями нет (LLM-запрос уже завершён). При выходе из приложения ход прерывается как обычно (семантика FSM running → paused) — pending-карточки не персистятся.
- **Vault-safety вместо .bak**: перезапись только после полного чтения файла в этом чате + mtime-guard (файл изменился снаружи → ERROR «перечитай»); delete — только в Корзину. bak-файлы засоряли бы Obsidian.
- **MCP-вызовы = write-уровень**: в режиме «Спрашивать» требуют подтверждения (закрыт п. 10 бэклога); прежнее поведение задачи 15 — режим «Авто». Зафиксировано в ARCHITECTURE.md.
- Классификатор команд консервативен: редиректы (`>`), подстановки (`` ` ``, `$(`), `--output` и любой сегмент вне allowlist → dangerous. Расширение allowlist — кнопкой «На сессию».
- Diff-превью в карточке approve строится теми же чистыми функциями, что и исполнение (`FileChangePreview`), с чтением диска вне главного потока.

Агентам следующих задач:
- Новые инструменты добавлять в `ToolRegistry.projectTools` И классифицировать в `ToolRiskClassifier.classify` (незнакомое имя = dangerous — защитный дефолт, но лучше явно).
- `ToolExecutor.execute` принимает опциональный `FileOpsContext`; без него write-инструменты честно отказывают — прямые вызовы исполнителя (пайплайны, будущие фичи) должны передавать контекст чата.
- Сессионный allowlist и `FileOpsContext` живут в `ChatViewModel` (in-memory per-чат) и чистятся в `deleteChat`.
- mtime-guard не видит несохранённый буфер открытого в редакторе файла — FSEvents подтянет изменение позже; для vault-файлов, открытых в редакторе приложения, возможна гонка «редактор перезапишет правку агента» (и наоборот — guard откажет агенту после автосохранения редактора; это желаемое поведение).
