# Задача 86: регулируемый пайплайн уверенности + видимые замеры в чате тюнинга

## Тип

фича

## Модель

Fable 5

## Цель

Пользователь сам тестирует оценку уверенности (домашка «День 7») и записывает видео —
приложение должно давать ему две вещи, которых нет после задачи 85:

1. **Регулировка пайплайна**: тумблеры подходов (constraint / redundancy / scoring /
   self-check) прямо во вкладке «Чат» — что включено, то и применяется к следующему
   сообщению. По умолчанию включён только constraint (мгновенный и бесплатный) —
   пользователь сам включает остальные и смотрит, как меняются вердикты, latency и cost.
2. **Видимые замеры**: панель «Статистика сессии» во вкладке «Чат» — агрегаты по
   сообщениям текущего чата ровно в терминах домашки: сколько ответов отклонено (FAIL),
   сколько потребовало повторного инференса и сколько доп. вызовов всего, влияние на
   latency (средняя основная vs полная, наценка ×N) и cost (суммарные токены prompt +
   completion; локальный прогон — $0, поэтому cost выражается токенами и временем).

## Зависимости

85 (`[x]`).

## Допущения и corner-кейсы

- Дефолт конфигурации: constraint ВКЛ, redundancy/scoring/self-check ВЫКЛ — пользователь
  явно просил «не всё сразу»; включённое запоминается в `finetune-chat.json` (P2:
  `decodeIfPresent`, дефолт как выше, тест миграции — старый документ без поля).
- Тумблер действует только на новые сообщения; отчёты уже полученных не пересчитываются.
- Отключённый подход в отчёте — сигнал nil: редьюсер уже это умеет («недоступен» не
  влияет на вердикт), причин-строк «подход отключён» не добавлять — шум.
- Redundancy ВЫКЛ → ровно 1 основной вызов; ВКЛ → 3 полных ответа (как раньше).
- Все подходы ВЫКЛ (включая constraint) — допустимо: вердикт по нулю сигналов = UNSURE
  с причиной «ни один подход не включён»; extraCalls = 0.
- Статистика считается из `report` сообщений ассистента текущего чата на лету (чистая
  функция от `[TuningChatMessage]` — P1, без нового persisted-состояния); «Очистить чат»
  обнуляет и её. Сообщения, снятые при разных конфигурациях, честно попадают в общие
  агрегаты — это фича (видно влияние включения подходов), в панели дополнительно
  разрез «с доп. вызовами / без».
- «Повторного инференса потребовало» = сообщения с extraCalls > 0; «доп. вызовов всего» =
  сумма extraCalls. Наценка latency = среднее totalLatency / среднее primaryLatency
  по сообщениям с отчётом; при нуле сообщений панель скрыта.
- Батч-прогон (кнопки «Батч: …») намеренно НЕ регулируется — он для сравнения полного
  пайплайна baseline vs тюн; в UI подпись об этом.
- AX: тумблеры и панель отдают `accessibilityValue` (инвариант модуля).

## Архитектура

- `ConfidencePipelineConfig: Equatable, Codable` (P1, в `Confidence/`): 4 булевых поля +
  статический `default`. `ConfidencePipeline.run` принимает конфиг и пропускает
  выключенные стадии (redundancy: пропуск доп. send'ов; scoring/self-check: пропуск
  вызова → сигнал nil; constraint ВЫКЛ → проверки не считаются, ранний FAIL не работает).
- `TuningChatSessionStats` (P1, чистая функция `[TuningChatMessage] → Stats`):
  answered/rejected/unsure/ok, needingReinference, extraCallsTotal, avgPrimary/avgTotal,
  наценка, promptTokens/completionTokens.
- `TuningChatDocument` + поле `pipelineConfig` (дефолт см. выше).
- `TuningChatViewModel`: `@Published pipelineConfig` (персист через существующий
  `persistNow`), прокидывает в `ConfidencePipeline`; `sessionStats` — computed.
- UI (`FineTuneChatViews`): ряд тумблеров-чипов над полем ввода + `DisclosureGroup`
  «Статистика сессии» (или компактная строка) с перечисленными числами.

## Критерии приёмки

1. Тумблеры четырёх подходов в чате; выключенный подход не делает вызовов (счётчик
   вызовов мок-провайдера в тесте) и даёт nil-сигнал в отчёте.
2. Дефолт: только constraint; выбор переживает перезапуск; старый документ мигрирует.
3. Панель статистики показывает: отклонено, потребовало повторного инференса, доп.
   вызовов, среднюю latency осн./полную с наценкой, токены. Числа сходятся с отчётами
   сообщений (тест на чистой функции).
4. Redundancy ВЫКЛ → 1 вызов на сообщение; все ВЫКЛ → UNSURE «ни один подход не включён».
5. `./scripts/build.sh`, `./scripts/test.sh` зелёные; ревью GO.

## Отчёт тестов

Новое покрытие (+23 теста): пропуски стадий пайплайна по конфигу — счётчик вызовов
мок-провайдера (дефолт → 1 вызов; всё включено → 5; redundancy/scoring/self-check
выключаются по отдельности; constraint ВЫКЛ → ранний FAIL невозможен; все ВЫКЛ →
UNSURE «ни один подход не включён» и 1 вызов); `TuningChatSessionStatsTests` — 10 тестов
таблицей (пусто → nil, сообщения без report не считаются, смешанные вердикты, наценка
latency, разрез «с доп. вызовами / без», токены); миграция `pipelineConfig`
(старый документ без поля → дефолт) + round-trip; VM-тесты адаптированы под продовый
дефолт явным `.allEnabled`. Правка редьюсера нейтральна для старых кейсов: пустые
`constraintChecks` до задачи 86 были недостижимы (обе формы проверок возвращают ≥2),
существующие тесты редьюсера прошли без правки ожиданий.

Итог `./scripts/test.sh`: **1618 тестов, 0 падений, 1 пропущен** (live-harness).

## Результат

Тумблеры четырёх подходов уверенности в чате тюнинга (дефолт — только constraint,
выбор персистится), панель «Статистика сессии» с замерами домашки (отклонено /
повторные инференсы и доп. вызовы / latency осн. vs полная с наценкой / токены),
батч намеренно всегда полный. `chat-tests.md` размечен категориями (корректные /
пограничные / сложные-шумные) и дополнен инструкцией снятия замеров. Финальное
тестирование и запись видео — за пользователем (его явное решение).
