# Задача 54: переименование заметки чинит `[[ссылки]]`

## Цель

Пользователь переименовывает заметку в дереве vault — и все `[[ссылки]]` на неё в других
заметках автоматически указывают на новое имя, ничего не ломается. Сейчас после
переименования эти ссылки становятся битыми, и их приходится править руками.

## Зависимости

04 (Wikilinks и backlinks: `LinkIndex` хранит вхождения с точным `NSRange` и `sourceFile`,
`backlinks(to:)`/`resolve` уже есть — прицел на эту задачу заложен в 04).

## Объём

1. Чистое ядро переписывания (P1), новый файл `Sources/SecondBrain/Links/LinkRewriter.swift`:
   по тексту заметки-источника и вхождению `[[...]]` (`Wikilink.range`, `target`, `alias`,
   `heading`) + новое имя цели → новый текст, где заменён **только сегмент цели** внутри
   `[[...]]`; алиас после `|`, заголовок после `#` и папка-префикс `папка/` сохраняются.
   Функция без I/O — тестируется таблицей случаев.
2. `Sources/SecondBrain/Vault/VaultFileOperations.swift` — метод атомарной перезаписи
   содержимого существующего `.md` (сейчас его нет: есть create/rename/move/trash/
   writeConflictCopy, но не «перезаписать текст»). Запись `.atomic`, единственная точка
   изменения файлов vault (инвариант №1).
3. `Sources/SecondBrain/Vault/VaultManager.swift` — расширить `rename(_:to:)`: собрать
   `backlinks(to:)` для переименовываемого файла, переименовать файл, затем переписать
   сегмент цели в каждом файле-источнике через ядро из п.1 и метод из п.2; ошибки записи
   отдельных файлов копятся и доводятся до UI через `lastError`; по завершении обновить
   индекс и `linkVersion`.
4. `Sources/SecondBrain/Links/LinkIndex.swift` — переиспользуется как есть; изменения,
   вероятно, не требуются (перепроверить: `backlinks(to:)` даёт ровно нужные вхождения).
5. UI: `Sources/SecondBrain/Vault/VaultViews.swift` — поведение добавляется в существующий
   поток переименования (TextField «Новое имя» → `manager.rename`); новый UI-элемент не нужен.
6. Тесты: юнит-таблица ядра в `Tests/SecondBrainTests/LinksTests.swift` (или новый
   `LinkRewriterTests.swift`); интеграционный тест реального пути rename в
   `Tests/SecondBrainTests/VaultTests.swift` (temp-vault: несколько заметок со ссылками →
   переименование → проверка содержимого файлов-источников).

## Вне объёма

- Embed `![[...]]` — `WikilinkParser` их сознательно не разбирает (см. его заголовок), значит
  они и не чинятся; отдельно ничего для них не делаем.
- Markdown-ссылки вида `[текст](путь.md)` — проект их в графе ссылок не поддерживает
  (только `[[...]]`); не трогаем.
- Обновление ссылок при **перемещении** заметки в другую папку (`move(_:into:)`) — отдельная
  возможная задача, не здесь.
- Массовое переименование, история/undo операции, изменение алиасов, ссылки внутри код-блоков
  (парсер их и так исключает).

## Критерии приёмки

- Интеграционный тест: в temp-vault заметка `Old` с входящими `[[Old]]` из нескольких других
  заметок; после `rename(Old → New)` все эти файлы на диске содержат `[[New]]`, файл
  переименован, битых ссылок не осталось.
- Юнит-таблица ядра проходит на случаях: bare `[[Old]]`→`[[New]]`; алиас `[[Old|подпись]]`→
  `[[New|подпись]]` (алиас цел); заголовок `[[Old#Раздел]]`→`[[New#Раздел]]` (заголовок цел);
  path `[[папка/Old]]`→`[[папка/New]]` (префикс цел); кириллические имена и пути; ссылка внутри
  ```` ``` ````-блока НЕ тронута; при дублях имени правятся только вхождения, резолвящиеся в
  переименовываемый файл.
- Регистр цели в переписанной ссылке берётся из нового имени файла.
- Битый ввод (пустое имя, имя с «/», уже существующее имя) → `rename` завершается ошибкой в
  `lastError`, файлы-источники **не** изменены (ссылки правятся только после успешного
  переименования файла).
- Ошибка записи одного из источников не отменяет остальные и не откатывает переименование:
  собранные ошибки уходят в `lastError`, данные не теряются.
- `./scripts/build.sh` и `./scripts/test.sh` зелёные.

## Допущения и corner-кейсы

Автономный режим: вопросы не задавались, ниже — принятые допущения.

- **Сценарий.** Пользователь переименовывает заметку из дерева vault (`VaultViews`, поле
  «Новое имя»). До: заметка с входящими `[[ссылками]]` из других заметок. После: файл
  переименован, во всех заметках-источниках `[[ссылка]]` указывает на новое имя, битых нет.
- **Форма ссылки — сохраняем как написано.** Правится только сегмент цели: bare `[[Old]]`→
  `[[New]]`, path `[[папка/Old]]`→`[[папка/New]]` (папка-префикс сохраняется). Алиас после
  `|` и заголовок после `#` не трогаем. Регистр новой цели — из нового имени файла.
- **Дубли имён.** В vault могут быть две заметки `Old` в разных папках. Чиним **только** те
  вхождения, что реально резолвятся в переименовываемый файл, — их и возвращает
  `backlinks(to:)` (bare `[[Old]]` резолвится глобально в один файл; path `[[папка/Old]]` — по
  пути). Ссылки на однофамильца в другой папке остаются нетронутыми.
  - *Известное ограничение (не чиним в этой задаче):* если после переименования имя `New`
    уже занято другой заметкой, стоящей короче по пути, свежая bare-ссылка `[[New]]` может
    начать резолвиться в неё. Это редкий случай коллизии имён; предупреждение/выбор здесь не
    делаем.
- **Порядок операций.** Сначала собираем вхождения (`backlinks(to:)` по старому URL), затем
  атомарно переименовываем файл, и только при успехе переписываем источники. Если
  переименование файла падает (пустое имя, «/», `alreadyExists`) — ни один источник не тронут,
  ошибка в `lastError`. Между сбором вхождений и переписыванием источники не меняются, поэтому
  сохранённые `NSRange` остаются валидными.
- **Битый/пустой/огромный ввод.** Пустое имя и имя с «/» отсекает существующая `validate` в
  `VaultFileOperations`; имя-дубликат → `alreadyExists`; все три доходят до пользователя через
  `lastError`, ссылки не правятся. Сотни входящих ссылок — операция best-effort, каждая запись
  атомарна; искусственного лимита не вводим (типичный vault укладывается без проблем).
- **Ошибки записи / нет прав.** Переписывание источников best-effort: недоступный или
  незаписываемый файл-источник не отменяет остальные. Ошибки копятся и доводятся до UI через
  `lastError`; переименование самого файла уже выполнено — частичный успех данные не теряет
  (индекс пересоздаваем, битые вхождения видны в backlinks).
- **Файл-источник открыт в редакторе с несохранёнными правками.** Внешняя запись на диск
  сработает mtime-guard редактора (существующее поведение — conflict-copy через
  `writeConflictCopy`); отдельной логики не добавляем.
- **Краш посреди операции.** Индекс связей в памяти, пересоздаваем: на старте перестроится из
  vault. Незавершённая пачка правок (часть источников обновлена, часть — нет) допустима: данные
  не потеряны, недочищенные ссылки просто останутся битыми до повторного переименования.
- **Два окна / пайплайн одновременно.** Для ручного переименования маловероятно. Запись идёт
  через единую точку `VaultFileOperations`; специальной блокировки для этой задачи не вводим.
- **Миграция.** Производных данных на диске нет (индекс живёт в памяти) — миграция не нужна.
- **Как проверю руками.** В реальном/тестовом vault: заметка `A` со ссылкой `[[Old]]` →
  переименовать `Old` в `New` → открыть `A`, увидеть `[[New]]` и рабочий переход по ссылке.

## Архитектура

### 1. Куда ложится и что переиспользуем

Задача целиком в модулях `Links/` (чистое ядро + расширение парсера) и `Vault/`
(оркестратор + новая файловая операция). Новых подсистем нет.

Переиспользуется как есть:
- `LinkIndex.backlinks(to:)` (`Sources/SecondBrain/Links/LinkIndex.swift:112`) — уже
  отдаёт **ровно** нужные вхождения: фильтр `resolve(occurrence.link.target)?.path ==
  targetPath` означает, что вернутся только ссылки, реально резолвящиеся в
  переименовываемый файл (bare-имя резолвится глобально в один файл, path — по пути;
  дубли-однофамильцы в других папках отсеяны). Каждый `LinkOccurrence` несёт `sourceFile`
  и `Wikilink` с точным `NSRange`.
- `LinkIndex.refresh()` (`:64`) и `linkVersion` — для обновления индекса/UI после пачки.
- `WikilinkParser.parse` — ядро парсит текст заново (см. п.4).
- `VaultFileOperations.rename`/`validate` — переименование файла и отсев битых имён.

Создаётся заново: `LinkRewriter` (ядро), `VaultFileOperations.overwrite` (атомарная
перезапись), кастомный `VaultManager.rename`, поле `Wikilink.targetRange`.

`LinkIndex.swift` **не меняется** — перепроверено, `backlinks(to:)` достаточно.

### 2. Граница «ядро ↔ оркестратор»

- **Оркестратор `VaultManager.rename(_:to:)`** решает, *какие* вхождения чинить: резолв
  дублей и short-path-winner — это глобальное знание индекса, локально невоспроизводимо.
  Он собирает вердикт из `backlinks(to: oldURL)` в набор литеральных целей
  `Set(occ.map { $0.link.target.lowercased() })`, делает I/O (rename файла, чтение/запись
  источников), копит ошибки, дёргает индекс. Резолв-вердикт передаётся в ядро **строками
  целей**, а не URL: это сохраняет нюанс «кто победил по кратчайшему пути» (набор строится
  из того, что реально резолвилось).
- **Ядро `LinkRewriter`** — текстовая хирургия над одним файлом-источником: без I/O, без
  индекса, без резолва. Заменяет только сегмент цели, сохраняя папку-префикс, `#heading`,
  `|alias` и все пробелы.

### 3. Как заменить ТОЛЬКО сегмент цели — решение (б)

Вариант **(б): расширить `Wikilink` полем `targetRange: NSRange`** — range-хирургия в духе
эталонов (`VaultPath`, инкрементальная подсветка). Парсер уже вычисляет этот диапазон в
`parseInner` (`WikilinkParser.swift:105`, `let targetRange`), нужно только пробросить его в
конструктор `Wikilink(...)` на строке 124. Вариант (а) (реконструкция `[[` + parts + `]]`)
отклонён: он теряет исходное форматирование внутри скобок (`[[ Old ]]`, `[[Old | alias]]`) —
это молчаливое переписывание чужого текста, против инварианта №1.

Важно: для path-цели `[[папка/Old]]` менять надо **не весь** `targetRange`, а только
последний компонент после последнего `/`. Ядро вычисляет под-диапазон из `targetRange`
+ позиции последнего `/` (в UTF-16); для bare-цели `/` нет → весь `targetRange`.
Папка-префикс, `#`, `|` остаются байт-в-байт.

Последствия (объём правок мал — это подтверждает правильность (б)):
- `Wikilink(` конструируется в **3 местах**: `WikilinkParser.swift:124` (прод, значение
  уже есть локально), `MarkdownEditorView.swift:992` `shifted(_:by:)` (прод — добавить
  `targetRange: s(link.targetRange)`), `IncrementalHighlightTests.swift:50` `shiftLink`
  (тест — аналогично). Всё механически.
- `Equatable` синтезированный → станет сравнивать и `targetRange`. `IncrementalHighlight`
  сравнивает `rebuiltLinks == expectedLinks`; оба идут через parse + согласованный сдвиг,
  абсолютные позиции совпадают → равенство сохраняется.

### 4. Сигнатура ядра (таблично-тестируемая)

```swift
enum LinkRewriter {
    /// Переписывает сегмент цели у всех [[ссылок]], чья цель (регистронезависимо)
    /// входит в `oldTargets` — точные строки target из backlinks(to:), где резолв
    /// уже сделан индексом. `newBaseName` — новое имя без папки и расширения.
    /// Сохраняет папку-префикс, #heading, |alias и пробелы. Возвращает исходный
    /// текст без изменений, если менять нечего.
    static func rewrite(in text: String,
                        oldTargets: Set<String>,
                        newBaseName: String) -> String
}
```

Решение по stale-ranges: ядро **парсит текст заново** (`WikilinkParser.parse(text)`),
а не принимает готовый список `NSRange` из индекса. Так надёжнее к рассинхрону —
диапазоны всегда свежие, — и проще для таблицы: вход `(text, Set<String>, newBaseName)`
→ выход `text`, в стиле `ToolPermissionsTests`. Резолв-вердикт при этом не теряется: он
закодирован набором строк `oldTargets` (только то, что реально резолвилось), а bare-резолв
глобален. Отбор внутри ядра: `links.filter { oldTargets.contains($0.target.lowercased()) }`.

### 5. Порядок мутаций — справа налево

Несколько ссылок в одном файле → замены применять **по убыванию `range.location`**
(справа налево) над `NSMutableString`, иначе после замены разной длины съедут диапазоны
левее нетронутых: `toRewrite.sorted { $0.range.location > $1.range.location }`, затем
`ns.replaceCharacters(in: сегмент, with: newBaseName)`. Это внутри ядра.

### 6. Инварианты под угрозой

- **Инвариант №1 (запись в чужие .md).** Новый метод — единственная точка изменения
  содержимого: `overwrite(_ url: URL, contents: String) throws` в
  `VaultFileOperations.swift` (`Data(contents.utf8).write(to:, options:.atomic)`), перезапись
  существующего файла на месте. Только через него.
- **mtime-guard редактора.** Если источник открыт с несохранёнными правками, внешняя запись
  сработает существующий conflict-detection `EditorViewModel` → conflict-copy. Своей логики
  не добавляем (в объёме прямо сказано).
- **Индекс и UI.** После пачки — **один** `linkIndex?.refresh()` (не пофайловый
  `updateFile`): он сам снимет старый путь переименованного файла, добавит новый и
  переиндексирует источники по mtime; дешевле и без пропущенных случаев, совпадает с
  существующим FSEvents-хендлером (`VaultManager.swift:130`, `:212`). Затем `linkVersion += 1`
  для панели backlinks и подсветки.
- **Порядок и best-effort.** Собрать backlinks по старому URL → `rename` файла (упал —
  `lastError`, источники не тронуты) → при успехе переписать источники best-effort, ошибки
  отдельных файлов свести в один `lastError`; переименование не откатываем.

### 7. Персистентность и миграция

Ничего на диск не персистится: `LinkIndex` живёт в памяти, пересоздаваем из vault. Меняется
только пользовательский .md-контент (это и есть цель). Store-миграция не нужна.

### Порядок работ (ядро → UI)

1. `Wikilink.targetRange` + проброс в `WikilinkParser.parseInner`; починить 2 сайта
   конструктора (`MarkdownEditorView`, `IncrementalHighlightTests`). Стоп-точка: сборка +
   тесты Editor/Links зелёные.
2. `LinkRewriter.rewrite(...)` (ядро, справа-налево, last-component-хирургия).
3. `LinkRewriterTests` — таблица. Стоп-точка: ядро закрыто без моков.
4. `VaultFileOperations.overwrite(_:contents:)` (атомарно).
5. Кастомный `VaultManager.rename(_:to:)`: backlinks → набор целей → rename → best-effort
   перезапись → `refresh()` + `linkVersion++`. `move` и прочий CRUD остаются на `perform`.
6. Интеграционный тест в `VaultTests`. UI (`VaultViews`) не трогаем.

### Риски

- **Editor-модуль хрупкий:** поле в `Wikilink` задевает инкрементальную подсветку —
  прогнать весь набор тестов Editor целиком, особенно `IncrementalHighlightTests`.
- **UTF-16 vs символы:** last-component-срез считать в UTF-16 (`NSString.range(of:"/")` по
  `targetRange`), иначе падение на кириллице/эмодзи.
- Ручная проверка: `[[Old]]` в заметке `A` → rename `Old`→`New` → в `A` виден `[[New]]`,
  переход работает; однофамилец `Old` в другой папке не тронут.

**В бэклог (вне объёма):** обновление ссылок при `move(_:into:)`; предупреждение о коллизии
имён, когда после переименования bare-`[[New]]` начинает резолвиться в другой короткий путь.

### Мелочи

## Результат

Реализовано: при переименовании заметки все входящие `[[ссылки]]` в других заметках
автоматически чинятся. Сделано поверх готового `LinkIndex` (задача 04 закладывала это —
у каждой ссылки хранится точный `NSRange`).

Что вошло:
- `Wikilink.targetRange` (`WikilinkParser.swift`) — точный UTF-16-диапазон сегмента цели
  (парсер уже считал его внутри, вынесли наружу); проброшен в 3 сайта конструктора.
- `LinkRewriter` (`Links/LinkRewriter.swift`) — чистое ядро (P1): по тексту источника,
  набору целей и новому имени переписывает **только** последний компонент цели внутри
  `[[...]]`, справа-налево над `NSMutableString`; алиас/`#heading`/папку-префикс/пробелы
  сохраняет; регистр — из нового имени файла.
- `VaultFileOperations.overwrite(_:contents:)` — атомарная перезапись существующего .md на
  месте (вторая — после `writeConflictCopy` — точка изменения содержимого vault, инвариант №1).
- `VaultManager.rename(_:to:)` переписан: собрать `backlinks(to:)` до переименования → набор
  целей → `rename` файла → при успехе best-effort переписать уникальные источники → один
  `linkIndex.refresh()` + `linkVersion++`. Падение rename → источники не тронуты; отказ записи
  одного источника → остальные обновлены, имя проблемного в `lastError`, откат не делается.

Отклонений от плана нет. `move(_:into:)` намеренно не трогает ссылки — вынесено в бэклог.
Известное ограничение: если после переименования bare-`[[New]]` начинает резолвиться в другой
файл с более коротким путём (коллизия имён) — не предупреждаем; в бэклоге.

UI не менялся: поведение вошло в существующий поток TextField «Новое имя» → `manager.rename`.
Проверено: сборка зелёная, 1052 теста / 0 падений; интеграционный тест реального rename-пути
на temp-vault подтверждает переписывание bare/alias/heading/path-ссылок и best-effort при
отказе записи (отказ смоделирован каталогом `0o555`, эмпирически небутафорский).
