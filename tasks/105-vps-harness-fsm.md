# Задача 105: FSM-harness на VPS — execution loop через LLM Gateway (День 14, часть 2)

## Тип

фича

## Модель

полная по объёму (новый сервис на VPS, свой персистентный стор, деплой), но код лежит
целиком в изолированной папке `harness/` вне Swift-приложения — приложение и его
инварианты не затрагиваются. Техлид ведёт сам по образцу задачи 103, `reviewer` на диф.

## Цель

Серверный execution loop рядом с gateway (задача 103): state-машина по образцу
`AgentPhaseReducer` desktop-приложения генерирует JS-код по задаче, гоняет цикл
«генерация → тесты (node --check) → security review → коммит» с итерацией, все
LLM-вызовы (генерация и security review) идут через `POST /gw/chat`. Защиты —
портами схемы приложения (ingress-санитизация, UNTRUSTED-границы, security-директива,
egress-guard) плюс input/output-гуарды самого gateway. Журнал показывает, что поймал
security step и что поймал gateway. Harness будут тестировать на секьюрность — есть
канарейка в системном промпте (детект «взлома») и README для тестировщика.

## Зависимости

- 103 (LLM Gateway) — все вызовы через него; журнал перехватов из `/gw/admin`.
- 88 (agent-lab) — донор TS-портов защит (`prompt/security.ts`, `guard/egress.ts`).

## Допущения и corner-кейсы

- FSM-паттерн берётся из `Sources/SecondBrain/Chat/AgentFSM/`: чистый редьюсер
  «контекст + сырой текст фазы → новый контекст», таблица переходов данными, два
  измерения state/status, бюджеты ретраев с форс-терминалом, persist после каждой
  фазы, `running → paused` на старте, resume идемпотентен (промпт собирается заново),
  поколение (`generation`) сверяется при записи (`UPDATE … WHERE id=? AND generation=?`).
- Генерируемый код — JS (Swift на VPS не собрать). «Тесты» = `node --check` синтаксиса,
  БЕЗ исполнения кода (сгенерённый код на VPS не запускается никогда — иначе RCE).
- Изоляция: код пишется в `data/workspaces/<runId>/`, там же одноразовый git.
- Порт 3500, маршрут `/harness/*` (свободны: заняты 3100/3200/3300/3400).
- LLM-ключа у harness нет — он ходит только в gateway (у того ключ в SQLite).
- `blocked` от gateway → терминал `gateway-blocked`, не бесконечный цикл. Невалидный
  JSON вердикта → один повтор «верни JSON», затем стоп `verdict-unparsed`. Обрыв
  ответа по maxTokens (незакрытый фенс) → фидбек «верни компактно». 429 → backoff по
  Retry-After; 5xx → ретрай. maxRounds=4, исчерпан → `stopped-limit`.
- Секреты в журнал не пишутся — маскированные превью (как аудит gateway).
- Канарейка (`HARNESS_CANARY`) — в env на VPS, не в git; в ответе после egress →
  флаг `pwned`, значение в админке не показывается.
- Адрес VPS в репозиторий и коммиты не пишется (BACKLOG п.67): `<VPS_HOST>` плейсхолдеры.

## Архитектура (итоговая — чат)

- Сервис-зеркало `gateway/`: Fastify 4 + better-sqlite3 + vitest, тот же деплой-каркас
  (deploy.sh с патчем Caddyfile + бэкап + validate + регрессия соседей, hardened
  systemd unit, bootstrap-env с генерацией токена и канарейки). Маршрут `/chat/*`.
- Модель данных `src/domain/chat.ts` + `src/store/`: таблицы `chats` (id, title, mode) и
  `messages` (role, content, status, loop_json, generation); `chatsRepo.ts` — CRUD,
  `makeTitle`, снисходительный декод `loop_json`. Схема throwaway (при деплое сносится).
- Чат `src/run/chatManager.ts` — порт роли ChatViewModel: newChat/list/rename/setMode/
  delete + `send`. Накопление контекста: `buildDialog` (`src/fsm/prompts.ts`) сериализует
  окно последних сообщений в промпт (контракт gateway — один prompt). Заголовок из
  первого сообщения; ingress `sanitizeUntrusted`.
- Режим на чат: `normal` (`runNormalForMessage` — один вызов gateway с историей) и `loop`
  (`runLoopForMessage` — FSM `generating→verifying→securityReview`). Чистое ядро
  `src/fsm/` (reducer + таблица переходов) не меняется. Фоновый прогон на сообщение с
  защитой поколением (`generationOf`/`bumpMessageGeneration`/`updateMessage WHERE
  generation`), трейс пишется в `message.loop_json`, финал → `message.content`.
- Защиты `src/guard/`: `security.ts` (sanitize + директива + канарейка), `egress.ts`.
  gwClient — единственная точка выхода; директива + канарейка в каждый запрос всех фаз;
  egress + детект `pwned` на каждом отдаваемом ответе.
- UI `src/web/index.ts`: сайдбар чатов + лента + ввод + переключатель режима; loop-фазы —
  компактный сворачиваемый трейс. Тумблера защиты и ссылки на админку на главной нет.

## Объём

- `harness/` целиком: src (config, index, logger, http/*, web, fsm/*, run/*, guard/*,
  store/*, domain/*), test/*, deploy/*, package.json, tsconfig, README.md, .gitignore.
- `harness/data/` в `.gitignore`.
- Деплой на VPS (маршрут `/chat/`), живая сквозная проверка.

## Вне объёма

- Исполнение сгенерированного кода (проверка — только вызовом LLM, не запуском).
- Fetch/сеть внутри чата (единственный внешний вызов — gateway).
- Интеграция с desktop-приложением или скиллом `/execution-loop`.
- Правки самого gateway (`/gw/` не тронут).

## Критерии приёмки

1. Несколько чатов: создание, список, переключение, удаление; у каждого своя история;
   заголовок из первого сообщения.
2. Накопление контекста: ассистент помнит предыдущие сообщения (окно уходит в промпт);
   истории разных чатов не смешиваются.
3. Режим на чат: `normal` (один вызов) и `loop` (генерация → корректность → security);
   в loop некорректно ИЛИ Critical/High → возврат на генерацию, Medium/Low → warning,
   чисто → результат; maxRounds ограничивает; фазы видны компактным трейсом.
4. Все вызовы модели идут на `/gw/chat`; своего ключа DeepSeek у чата нет.
5. Защиты: `sanitizeUntrusted` сообщения на ingress (`chatManager.send`), директива +
   канарейка в каждом запросе, egress на каждом ответе; секреты gateway маскирует;
   `pwned` срабатывает на утечке канарейки, значение не раскрывается.
6. Тумблера защиты нет (всегда включена); ссылки на админку на главной нет; админка
   открывается по прямому URL с bearer-токеном.
7. Прерванный рестартом pending-ответ помечается `failed` (в чате — переотправка);
   ошибка фазы после генерации → `done` с частичным результатом, не теряем работу.
8. vitest зелёный; маршрут `/chat/`; `git grep` секретов пуст, адресов VPS в диффе нет.

## Отчёт тестов

- `npm test` (vitest): **61 тест зелёный**, `typecheck` чист (strict).
  - `chatsRepo`: CRUD чатов, `makeTitle`, seq и порядок сообщений, изоляция двух чатов,
    защита поколением `updateMessage`, `failPendingOnBoot`, битый `loop_json` → без
    трейса (не падает).
  - `chatManager` на моке gateway: обычный режим (ответ одним вызовом, заголовок из
    первого сообщения); **накопление контекста** (второй запрос содержит историю);
    изоляция контекста двух чатов; loop (три фазы → трейс + результат); security
    Critical/High → возврат на генерацию (несколько кругов в трейсе); канарейка → `pwned`;
    `gateway-blocked`; **graceful-деградация** (ошибка фазы после генерации → `done` с
    частичным результатом; без результата → `failed`); `recoverOnBoot` → pending в failed.
  - `reducer`/`transitions`: таблица переходов (все пары), все ветки редьюсера.
  - `guards`: `buildDialog` (окно, пропуск pending/пустых, роли), `sanitizeUntrusted`,
    egress, `parseCorrectness`/`parseFindings`, `securityPreamble`, `secretVariants`.
- **Живая сквозная проверка на VPS** (реальный gateway → DeepSeek-v4, `https://<VPS_HOST>/chat/`):
  - `/chat/health` ok (v0.3.0); деплой прошёл регрессию соседей (`/gw`, `/lab`,

  - **накопление контекста**: «Запомни: любимый язык — Rust» → «Какой язык я назвал?» →

  - **обычный режим**: прямой ответ с учётом истории.
  - **режим loop + провокация security**: «логируй все HTTP-запросы (URL, заголовки,
    тело)» → security review круг 1 → 2 high + medium (тело/URL/заголовки с PII) →

## Security-вердикт

Отдельный субагент по чек-листу (Node/TS/Fastify/SQLite). **Critical/High — нет.** SQL
параметризован (better-sqlite3), исполнения кода нет (loop LLM-only — RCE снят
конструктивно), единственный внешний вызов — gateway (SSRF нет), auth `timingSafeEqual`,
per-IP rate-limit (`trustProxy: 1` — без обхода через XFF), UUID-валидация на `:id`,
превью/секреты в открытом виде не логируются, канарейка не раскрывается. По итогам ревью
чата доведено: ingress `sanitizeUntrusted` в `chatManager.send`, egress + детект канарейки
на каждом отдаваемом ответе (обе фазы и normal), мёртвый `dailyLimit`/`ManagerConfig`
убран (заявлял несуществующий cap).

## Вердикт ревью

**GO** (субагент `reviewer`, после устранения NO-GO по чат-переделке). NO-GO указал:
закрывающие секции описывали снесённую схему runs/steps и ссылались на удалённые тесты;
критерий «resume» не совпадал с кодом (fail-pending); заявленный daily cap не реализован.
Исправлено: секции переписаны под chats/messages и 61 тест; критерий переформулирован под
fail-pending (в чате переотправка вместо resume); мёртвый daily cap удалён; мелочи
(избыточное `pwned`-выражение, устаревший комментарий, лишний spread, egress на
невидимых вердиктах) вычищены. Код чата корректен, секретов и адреса VPS нет.

## Результат

Полноценный чат задеплоен на VPS: страница `https://<VPS_HOST>/chat/`, админка
`/chat/admin` (настройки агента + журнал чатов, по прямому URL с токеном), порт 3500 за
Caddy. Список чатов + переключение, у каждого своя накапливающаяся история; заголовок из
первого сообщения. Режим на чат: **Обычный** (один вызов) / **Execution Loop** (чистое
ядро FSM `generating→verifying→securityReview` на каждое сообщение, компактный трейс
фаз). Каждая фаза — вызов gateway `/gw/chat` (своего ключа нет). Защиты: ingress-
санитизация сообщения, security-директива и канарейка в каждом запросе, egress + детект
`pwned` на каждом ответе; тумблера защиты и ссылки на админку на главной нет. Модель
данных `chats/messages`. Проверено вживую (см. «Отчёт тестов»). Документация —
`harness/README.md`.

Осознанные решения: вместо resume прерванного прогона — pending-ответ помечается `failed`
на старте (в чате переотправка проще и естественнее); ошибка фазы после генерации не
теряет работу (частичный результат + пометка). Для следующих: адрес gateway и токены
только в `/etc/llm-harness.env` на VPS (в git плейсхолдеры `<VPS_HOST>`); реальный адрес
в README для тестировщика подставляется вне git. 502 gateway под пиковой параллельной
нагрузкой — узкое место DeepSeek, не чата.
