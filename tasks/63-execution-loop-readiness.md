# Задача 63: пул задач + Execution Loop — готовность флоу к автономному циклу

## Тип

рефакторинг (процесс: правка правил/скиллов, без изменения кода приложения)

## Модель

sonnet (архитектурная работа над самим флоу, суждение о формулировках правил)

## Цель

Пользователь хочет запускать проект в режиме **Execution Loop**: одна команда — агент сам
берёт задачи из `tasks/00-INDEX.md` по очереди, сам выбирает профиль (`coder`/`bugfix`/
`refactor`) и уровень конвейера, выполняет, коммитит, берёт следующую — без вопросов и
правок между задачами. Разведка показала, что текущий флоу к этому не готов (см.
«Допущения и corner-кейсы»), и заодно подготовила материал для пула небольших задач.

## Зависимости

62 (гибкий конвейер, три уровня) — выполнена.

## Допущения и corner-кейсы

Из интервью с пользователем и разведки (3 параллельных Explore-агента):

- Коммит `execution-loop` — **только локальный**, без push/PR (решение пользователя;
  push/PR — отдельный шаг позже).
- Задача 47 (статус индекса доков) в пул не включается — средняя по размеру, с
  AX-смоуком, остаётся в индексе как есть на будущее (решение пользователя).
- Найдены и устранены три конкретных пробела текущего флоу:
  1. Правило «Одна сессия — одна задача» прямо противоречило идее очереди в одной сессии.
  2. `/task-run` не умел выбирать сценарный профиль — осознанный пробел, зафиксированный
     самой задачей 56 («Вне объёма») и `tasks/BACKLOG.md` п.29.
  3. Три стоп-точки флоу (незакрытые зависимости, два круга `NO-GO`, баг не
     воспроизвёлся) требовали человека без автономного fallback.
- Отдельно, по указанию пользователя в процессе ревью плана, добавлены два механизма,
  которых не было в первоначальной разведке:
  - **Изоляция контекста**: `execution-loop`, в отличие от одиночного `/task-run`,
    делегирует «Разработку» субагенту **на любом уровне** (включая малый) — иначе история
    инструментов копится в одной сессии на протяжении всей очереди задач.
  - **Экономия модели**: для задач с точно известным объёмом (файл/строка уже названы)
    дев-субагент запускается на `haiku` вместо модели сессии, с эскалацией до `sonnet`/
    `inherit` при повторном `NO-GO`. `reviewer` никогда не понижается.

## Результат

Выполнено. Все 7 пунктов «Объёма» реализованы:

- `CLAUDE.md`: добавлено исключение для `/execution-loop` в «Одна сессия — одна задача»;
  в «Сценарные профили» — таблица `## Тип → профиль` с оговоркой про `research`
  (терминален, не заменяет «Разработку»); строка `execution-loop` в таблице скиллов;
  краткий пересказ шаблона задачи включает `## Тип`/`## Модель`.
- `docs/CONVENTIONS.md`: шаблон файла задачи дополнен `## Тип` и `## Модель` с описанием
  маппинга на профиль/модель.
- `.claude/skills/task-run/SKILL.md`: стадия «Разработка» — профиль по `## Тип`, для задач
  без поля (заведённых до 63) — явный дефолт «фича/`coder`».
- `.claude/skills/execution-loop/SKILL.md` — новый скилл на 9 разделов: допуск, выбор
  задачи, уровень/профиль/модель, обязательное делегирование субагенту, ревью,
  NO-GO-эскалация, блокировка, закрытие (локальный коммит), стоп-условия (предохранитель
  3 подряд + финальный).
- `tasks/56-agent-scenario-profiles.md` (`## Тип: рефакторинг`, `## Модель: sonnet`) и
  `tasks/57-profile-benchmark.md` (`## Тип: документация`, `## Модель: haiku`) дополнены.
- 17 файлов `tasks/64-80.md` созданы по шаблону, зависимости `—` у всех (независимы, чтобы
  очередь не стопорилась).
- `tasks/00-INDEX.md`: 18 новых строк (63–80), без дублей номеров.

Отклонение от исходной разведки: нумерация пула сдвинута с изначально предложенных 63–79 на
64–80, поскольку 63 занята самой этой процессной задачей — коллизия найдена и исправлена
до записи файлов.

Что важно следующим агентам: `execution-loop` — это единственное место, где малая задача
идёт через субагента, а не делается техлидом сам (сознательное отступление ради контекста
цикла) — не путать с обычным `/task-run`, там малая по-прежнему solo. Модель дев-субагента
в пуле проставлена по признаку «объём точно известен» (файл:строка/один файл → `haiku`,
иначе `sonnet`) — если при реальном прогоне цикла окажется, что `haiku` систематически не
справляется даже с простыми задачами, стоит завести отдельную задачу на пересмотр порога, а
не тихо менять поле в каждом файле по одному.

Отчёт верификации: код (`Sources/`, `Tests/`) не тронут — `./scripts/build.sh`/
`./scripts/test.sh` не перезапускались, последний зелёный прогон (1089 тестов, 0 падений) —
из задачи 62. `git grep -I --cached -e 'sk-' -e 'ghp_' -e 'AIza'` по новым/изменённым
файлам — пусто (совпадения только в существующих скиллах/CLAUDE.md, где это сама
инструкция проверки, как и раньше).
