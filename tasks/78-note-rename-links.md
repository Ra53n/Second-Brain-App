# Задача 78: переименование заметки с обновлением ссылок

## Тип

фича

## Модель

sonnet

## Цель

Пользователь переименовывает заметку — все `[[wikilink]]`-ссылки на неё в остальном vault
должны обновиться автоматически, а не сломаться на битую ссылку (`tasks/BACKLOG.md` п.4).
`LinkIndex` уже умеет вычислять, какие файлы ссылаются на данный — не хватает операции
переименования, которая это использует, и UI-точки входа.

## Зависимости

Нет.

## Допущения и corner-кейсы

- **Область применения — только заметки.** «Переименовать» в контекстном меню уже
  существует (задача 02) и работает для любого узла дерева (файл или папка). Ссылки
  обновляются только когда переименовываемый узел — не папка и имеет расширение `.md`;
  для остальных узлов (папки, вложения, произвольные файлы) поведение не меняется —
  это ровно та же операция, что и раньше (`VaultFileOperations.rename` без побочных
  эффектов на ссылки). Обоснование: `LinkIndex` резолвит цели по имени файла без
  расширения — переименование не-md файла не может быть целью wikilink в принципе, а
  переименование папок явно вне объёма задачи.
- **Диалог переименования не меняется.** Пользователь по-прежнему вводит полное имя с
  расширением (существующий alert), никакого нового UI-элемента не добавлено — «точка
  входа» из объёма задачи уже была на месте, задача расширяет её поведение под капотом.
- **Конфликт имени (уже существует файл с целевым именем).** `VaultFileOperations.rename`
  бросает `VaultError.alreadyExists` ДО того, как затронуты файлы со ссылками — порядок
  операций в оркестраторе (`VaultManager.renameNote`) специально такой: сначала
  файловый `rename` (может провалиться), и только при его успехе — правка backlink-файлов.
  Ничего не переименовано и ни один чужой файл не тронут — доказано тестом
  `testRenameNoteToExistingNameFailsWithoutTouchingLinks`.
- **Ссылка с alias.** `[[Старое|Название]]` → `[[Новое|Название]]`: alias — константа,
  переносится как есть, меняется только `target`. Аналогично `#Заголовок` (секция внутри
  заметки) не переименовывается вместе с файлом — секции физически не переехали.
- **Ссылка с путём** (`[[Папка/Старое]]`, актуально при дублирующихся именах в разных
  папках): заменяется только последний компонент, префикс папки сохраняется — переименование
  папок вне объёма, значит путь к папке неизменен.
- **Битая ссылка на несуществующую заметку.** Не в объёме операции: `LinkIndex.backlinks(to:)`
  возвращает только вхождения, которые резолвятся именно в переименовываемый файл; ссылка
  на несуществующее имя никогда не входит в этот список и не трогается — она была и
  остаётся битой, это поведение вне контроля операции переименования (соответствует
  формулировке задачи «не трогать»).
- **Самоссылка** (заметка ссылается сама на себя): `LinkIndex.backlinks(to:)` уже
  исключает self-links (см. `testSelfLinksExcludedFromBacklinks` в `LinksTests.swift`) —
  переименование не пытается переписать содержимое самой переименовываемой заметки.
- **Несколько вхождений ссылки в одном файле.** Правки применяются по убыванию
  `range.location` (от конца текста к началу), чтобы более ранняя правка не сдвигала
  диапазоны последующих — покрыто `testApplyRewritesMultipleOccurrencesInSameFile`.
- **Два одновременных запуска / гонка с внешней правкой файла — исправлено после NO-GO
  первого круга ревью.** Первая версия этого пункта разбирала гонку только в одном
  направлении («внешняя правка может быть потеряна, last-write-wins») и упускала более
  серьёзный риск в другом: `NSRange`, закэшированный в `LinkIndex.backlinks(to:)` на момент
  индексации, применялся к тексту, ПЕРЕЧИТАННОМУ ЗАНОВО в момент записи — если файл
  изменился между индексацией и записью (правка в открытом редакторе, автосохранение
  которого дебаунсится 500 мс, внешний редактор, git-синк), диапазон мог указывать не туда:
  `NSMutableString.replaceCharacters(in:with:)` либо портит чужой текст молча (режет не то
  место), либо роняет процесс `NSInvalidArgumentException`/`abort()` — это не Swift `Error`,
  `try`/`catch` его не ловит. Реальный сценарий: правка одной заметки сдвигает офсет ссылки,
  следом почти сразу — переименование другой заметки, на которую эта ссылка ссылается.
  Починено: `NoteRenamePlanner.apply` перед каждым `replaceCharacters` сверяет диапазон со
  свежим текстом (`isStillValid` — в границах, начинается с «[[», содержит цель на момент
  индексации, `LinkRewrite.expectedTarget`); несовпавшее вхождение молча пропускается, не
  роняя файл и не блокируя применение остальных, ещё валидных, правок в том же файле.
  `linkIndex.refresh()` перед `backlinks(to:)` в `renameNote` дополнительно сужает (не
  устраняет) окно устаревания.
- **Прямая запись backlink-файлов в обход `VaultFileOperations` — исправлено.** Первая
  версия писала контент через `Data(...).write(to:options:.atomic)` напрямую, в обход
  `VaultFileOperations` — нарушение `Vault/CLAUDE.md` («все файловые операции — через
  VaultFileOperations») и антипаттерна 7. Добавлен `VaultFileOperations.overwrite(_:content:
  expectedMTime:)` — перезапись СУЩЕСТВУЮЩЕГО файла с mtime-guard: `expectedMTime` — снимок,
  снятый в момент чтения содержимого; если файл на диске изменился с тех пор (конкурентная
  внешняя правка), запись отклоняется `VaultError.operationFailed`, а не молча затирает
  чужие несохранённые изменения. Побочная находка при написании теста на эту защиту:
  `URL.resourceValues(forKeys:)` кэширует значение на самом значении `URL` — повторный вызов
  `modificationDate(of:)` на ТОЙ ЖЕ переменной `url` (ровно наш случай: снимок mtime при
  чтении и проверка mtime перед записью используют одну и ту же `url`) молча возвращал бы
  закэшированное значение, а не живое — guard сравнивал бы кэш сам с собой и никогда бы не
  сработал. `modificationDate(of:)` переписан через `FileManager.attributesOfItem`, кэша не
  имеющий.
- **`linkIndex == nil` на момент переименования — исправлено.** Переименование заметки до
  завершения фонового `Task.detached`, строящего `LinkIndex` при `openVault` (типично —
  сразу после открытия vault), раньше молча трактовалось как «нет входящих ссылок» (`?? []`)
  и переименовывало без единой правки ссылок, без ошибки пользователю. Теперь —
  явный отказ `VaultError.operationFailed` («индекс ссылок ещё строится, попробуйте
  переименовать через секунду»): ждать готовности индекса синхронно в `rename(_:to:)` не
  стали — усложнило бы сигнатуру (async) ради окна в доли секунды при типичном размере
  vault, отказ с понятной причиной дешевле и достаточен.
- **Частичный отказ записи одного из backlink-файлов** (диск недоступен, права, файл
  исчез между построением индекса и записью, либо конкурентная правка не прошла
  mtime-guard) — по-прежнему не откатывает уже переименованный файл и уже переписанные
  backlink-файлы (тот же подход, что у `perform` в `VaultManager`), но теперь ошибки по
  каждому файлу копятся и объединяются в один `VaultError.operationFailed` после того, как
  обработаны ВСЕ файлы (не прерывается на первом же отказе, как было раньше) — остальные
  валидные правки применяются, а не теряются из-за одного проблемного файла.
- **Пустой список backlinks.** Заметка без входящих ссылок переименовывается как обычно,
  `NoteRenamePlanner.rewrites` возвращает пустой список, `applyLinkRewrites` не трогает
  ни одного постороннего файла — обычный путь `VaultFileOperations.rename`, доказано тем,
  что `testCreateNoteSelectsResultAndReportsErrors` (без единой ссылки в vault) продолжает
  проходить через новый код без изменений в его ожиданиях по существу; тест обновлён только
  добавлением ожидания готовности `LinkIndex` перед rename — иначе он бы падал на новом
  явном отказе «индекс ещё строится» (см. пункт про `linkIndex == nil` выше), а не проверял
  бы то, для чего написан (конфликт имени).
- **Переименование в то же самое имя** (`target == url`, no-op в `VaultFileOperations.rename`):
  унаследовано от существующей реализации, для заметок в этом случае `backlinks` тоже
  посчитаются и перепишутся тем же текстом (идемпотентно, без потери данных) — отдельно не
  тестировалось, риска нет (результат текстуально идентичен исходному).

  переименования/перемещения), с mtime-guard: если файл на диске изменился с момента чтения

  конкурентную правку молча (см. `## Допущения и corner-кейсы`).

**Новый код:**

1. `Sources/SecondBrain/Links/NoteRenamePlanner.swift` — чистое ядро (P1), без I/O:
   - `LinkRewrite` — DTO «диапазон `[[...]]` в конкретном файле → новый текст ссылки» +
     `expectedTarget` (цель ссылки на момент индексации — для сверки со свежим текстом).
   - `NoteRenamePlanner.rewrites(for backlinks: [LinkOccurrence], newName: String) ->
     [LinkRewrite]` — на входе уже посчитанный список backlinks, чисто вычисляет новый текст

     `/`, `heading` и `alias`).
   - `NoteRenamePlanner.isStillValid(_ rewrite: LinkRewrite, in ns: NSString) -> Bool` —
     диапазон в границах СВЕЖЕГО текста, начинается с «[[» и содержит `expectedTarget`.
     Защита от устаревшего `NSRange` (добавлено после NO-GO — см. `## Допущения`).
   - `NoteRenamePlanner.apply(_ rewrites: [LinkRewrite], to text: String) -> String` —
     применяет к СВЕЖЕМУ тексту только прошедшие `isStillValid` правки, по убыванию
     `range.location` (защита от сдвига смещений при нескольких ссылках в одном файле);
     остальные молча пропускает.
   - Все функции чистые: тестируются без ФС и без `VaultManager` (`NoteRenamePlannerTests`
     в `Tests/SecondBrainTests/LinksTests.swift`).

2. `Sources/SecondBrain/Vault/VaultFileOperations.swift` — новый метод в существующем модуле
   CRUD (не отдельный файл, п.3 объёма задачи):
   - `modificationDate(of url: URL) -> Date?` — через `FileManager.attributesOfItem`, не
     `URL.resourceValues` (у последнего свой кэш на значении `URL`, переживающий повторные
     вызовы на той же переменной — ровно наш случай чтения/проверки mtime, см. `##
     Допущения»).
   - `overwrite(_ url: URL, content: String, expectedMTime: Date?) throws -> URL` —
     перезапись содержимого существующего файла с mtime-guard, атомарная запись.

3. `Sources/SecondBrain/Vault/VaultManager.swift` — тонкий оркестратор:
   - `rename(_:to:)` разветвляется: папки и не-`.md`-файлы — старый путь
     (`perform { VaultFileOperations.rename(...) }`, не изменился); `.md`-файлы —
     `renameNote(_:to:)`.

     не выполняется вообще; иначе `linkIndex.refresh()` (сужает окно устаревания) →

     бросить `.alreadyExists` — тогда `applyLinkRewrites` не вызывается) → `applyLinkRewrites`
     → `open(target)` + финальный `linkIndex.refresh()` (подхватывает переименованный файл и
     переписанные backlink-файлы по mtime).
   - `applyLinkRewrites(_ rewrites:)` — группирует по файлу-источнику, на файл вызывает
     приватную перегрузку; ошибки по отдельным файлам копятся в массив и не прерывают
     обработку остальных, в конце — один `VaultError.operationFailed` со всеми, если были.
   - `applyLinkRewrites(_ fileRewrites:, to file:)` — снимает mtime, перечитывает текст,
     `NoteRenamePlanner.apply` (сам отсеивает устаревшие вхождения), если текст не изменился
     (все вхождения устарели) — не пишет вовсе; иначе `VaultFileOperations.overwrite` с тем
     же mtime-снимком.

1. Найти в `Sources/SecondBrain/Links/` и `Sources/SecondBrain/Vault/` существующие типы
   для вычисления backlinks (`LinkIndex` или аналог) и для файловых операций
   (`VaultFileOperations` — по инварианту №1, запись в vault только через него).
2. Реализовать операцию переименования: переименовать файл через `VaultFileOperations`,
   обновить `[[старое-имя]]` → `[[новое-имя]]` (и `[[старое-имя|alias]]` с сохранением
   alias) во всех файлах, где есть входящая ссылка по данным `LinkIndex`.
3. UI-точка входа: контекстное меню заметки (там, где уже есть другие файловые операции —
   удаление/перемещение) — «Переименовать» с обновлением ссылок.
4. Corner-кейсы: конфликт имён (целевое имя уже занято — не переименовывать, показать
   ошибку), ссылка с алиасом, битая ссылка на несуществующую заметку (не трогать).

## Результат

Переименование `.md`-заметки теперь обновляет входящие `[[wikilink]]`-ссылки (включая
alias/heading/путь-префикс) во всех файлах vault, используя существующие `LinkIndex`/
`VaultFileOperations`/UI-точку входа (задача 02) — новый код только в
`NoteRenamePlanner.swift` (чистое ядро), `VaultFileOperations.overwrite` и
`VaultManager.renameNote`.

Два круга ревью. Первый — серьёзный NO-GO по инварианту №1: устаревший `NSRange` из кэша
`LinkIndex` мог молча испортить чужой файл или уронить процесс (`abort()`, не Swift
`Error`), плюс запись backlink-файлов шла в обход `VaultFileOperations` без mtime-guard.
Оба устранены: `isStillValid` проверяет каждый диапазон против свежего текста перед
применением; новый `VaultFileOperations.overwrite` с mtime-guard (при этом найдена и
исправлена побочная фиктивность защиты — `URL.resourceValues` кэшируется на переменной
`URL`, заменено на `FileManager.attributesOfItem`). Второй круг — `GO`, оба блокирующих
пункта подтверждены нетривиальными тестами (7 новых), не только словами.

UI-смоук не прогнан живьём — известная проблема AX на этой машине (задачи 75/77) плюс
`ui.sh` в принципе не умеет работать с контекстными меню; поведение подтверждено
трассировкой «меню → функция» и интеграционными тестами на уровне `VaultManager`.
