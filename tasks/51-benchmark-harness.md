# Задача 51: бенчмарк-гарнесс для оценки конфигов

## Цель

Появляется способ измерить, что правила проекта, субагенты и скиллы (задачи 44–50) реально
повышают качество работы агента, а не просто занимают контекст. Одна боевая задача, два
прогона от одинаковой базы с разными версиями конфигов, сравнение по рубрике — с диффами,
пригодными для скриншота, и списком того, что сильнее всего повлияло на результат.

## Зависимости

44 (правила), 45 (субагенты), 46 (скиллы), 48 (экономия токенов) — все выполнены.

## Объём

1. `bench/PROMPT.md` — фиксированный промпт боевой задачи (переименование заметки с
   обновлением `[[ссылок]]`): голосом пользователя, называет симптом, запрещает вопросы,
   требует задокументировать допущения. Внутренних имён типов и путей не содержит.
2. `bench/EXPECTED.md` — ключ оценки (агенту не показывается): формы ссылок, ловушки,
   требования инварианта №1, corner-кейсы переименования, инженерные ожидания.
3. `bench/RUBRIC.md` — 10 измерений по 0–3 балла, продукт (1–8) и процесс (9–10) отдельно;
   ранжированная дельта между генерациями = драйверы качества.
4. `bench/capture.sh <label> [base]` — захват результата генерации: `.patch` (включая
   незакоммиченное), `.html` для скриншота, `-stats.txt`.
5. `bench/render_diff.py` — свой self-contained рендер юнифайд-диффа (без CDN и внешних
   ресурсов): шапки файлов, номера строк, подсветка +/−, светлая и тёмная темы.
6. `bench/RESULTS.md` — шаблон итога сравнения.
7. `bench/README.md` — протокол воспроизводимости и правила чистоты эксперимента.
8. `bench/.gitignore` — `out/` в git не хранится.
9. Тег `bench-base` на коммите гарнесса — общая точка старта обеих генераций.

## Вне объёма

- Реализация самой боевой задачи (переименование + ссылки): это предмет измерения, её делает
  бенчмаркуемый агент в отдельной сессии.
- Файл `tasks/NN` для боевой задачи: его создание входит в оцениваемое поведение (фазы Ф1–Ф3).
- Автоматическое выставление баллов: оценка ручная по рубрике — она про смысл, не про метрики.
- Прогон генераций: запускает пользователь отдельными сессиями.

## Критерии приёмки

- `capture.sh` на реальном диффе даёт валидный патч, открывающийся HTML и верную статистику.
- HTML self-contained: ни одной внешней ссылки, ни одного `<script>`.
- `PROMPT.md` не содержит внутренних имён (`LinkIndex`, `WikilinkParser`, путей `Sources/`).
- `swift build` и `swift test` не затронуты (изменения вне `Sources/` и `Tests/`).
- Тег `bench-base` поставлен.

## Результат

Сделано по плану.

- `bench/`: PROMPT (боевая задача), EXPECTED (28 пунктов ключа), RUBRIC (10 измерений),
  RESULTS (шаблон), README (протокол), `capture.sh` + `render_diff.py`, `.gitignore`.
- Самопроверка на реальном диффе (коммит задачи 50): 18 секций файлов, +725/−25, 23 ханка,
  922 номера строк, ноль внешних ссылок; страница проверена глазами в браузере — читается
  как GitHub-дифф и нормально скриншотится в тёмной и светлой теме.
- Тег `bench-base` поставлен на коммит гарнесса.

Обоснование выбора боевой задачи: `VaultManager.rename` → `VaultFileOperations.rename`
перемещает файл и **не трогает wikilinks** — после переименования все ссылки на заметку
становятся битыми (подтверждено чтением кода, пункт 4 бэклога). Задача задействует ровно то,
что описывают конфиги: данные уже есть (`LinkIndex.backlinks`, `WikilinkParser`), затрагивается
самый опасный инвариант (массовая правка чужих файлов), есть чистое ядро, тесты, UI и смоук.

Решения пользователя, зашитые в гарнесс: агент работает **автономно, без вопросов** (промпт
запрещает) — измеряем, сохраняется ли мышление про corner-кейсы, когда канал вопросов закрыт;
ось сравнения — конфиги v1 → доработка → v2.

Доработка по ходу: `capture.sh` сохраняет генерацию **веткой** `bench/<label>`, а не только
патчем — дифф читается штатными инструментами (`git diff bench-base..bench/gen1`, Claude Code,
IDE), генерации сравниваются напрямую (`git diff bench/gen1..bench/gen2`), а откат `main` больше
ничего не теряет. Незакоммиченный агентом хвост скрипт коммитит на ветку сам. HTML остаётся
только для скриншотов и шеринга.

Важно для следующих задач:

- **Не создавай `tasks/NN` для переименования со ссылками заранее** и не чини этот баг между
  прогонами: пропадёт предмет измерения. Бэклог п. 4 остаётся открытым намеренно.
- Работа генераций в `main` не остаётся: после `capture.sh` — всегда откат к тегу. Понравившуюся
  реализацию применять из `out/<label>.patch` отдельной задачей.
- Чистота эксперимента ломается от одного лишнего сообщения агенту в ходе прогона — правила
  в `bench/README.md`.
