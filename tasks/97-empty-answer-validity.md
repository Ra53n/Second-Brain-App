# Задача 97: пустой ответ — валидный кейс (self-check, нормализация {}, честные причины)

## Тип

багфикс (малая: чистое ядро + пайплайн, персистентность/UI/батч-раннер не меняются)

## Модель

Fable 5

## Цель

Фрагмент без поручений — валидный кейс: корректный `{"action_items": []}` не должен
получать FAIL из-за самопроверки, спрашивающей бессмыслицу; вырожденный `{}` модели
трактуется как пустой список с предупреждением (UNSURE, не FAIL); причины «недоступна»
не появляются для выключенных тумблеров (включая отчёт эскалации, где повторы
принудительно выключены).

## Зависимости

85–86 (пайплайн), 91 (эскалация). Выполнены.

## Допущения и corner-кейсы (по живым данным пользователя)

- Живой баг 1: `{"action_items": []}` → FAIL «Самопроверка: не подтверждено N из N» —
  пайплайн зовёт per-item self-check при 0 пунктов, модель выдумывает пункты, парсер
  игнорирует `expectedCount` и считает выдуманное.
- Живой баг 2: модель (3B и 7B) на пустых кейсах отвечает `{}` → hard-fail «валидный
  JSON», хотя семантика однозначна.
- Путаница 3: «Сверка повторов недоступна» в показанном отчёте при включённом
  тумблере — отчёт от ступени эскалации, где redundancy принудительно off (задача 91);
  редьюсер пишет «недоступна» для любого nil-сигнала, не отличая «выключено».
- Нормализация: только вырожденный пустой объект (`{}` с любыми пробелами — через
  JSONSerialization: пустой словарь) → канонический `{"action_items": []}`; всё
  остальное — как раньше. Нормализованный текст показывается в чате и уходит во все
  проверки/повторы; предупреждение в reasons, вердикт не лучше UNSURE (каскад дальше
  сам решает — после 95 без риска ухудшения).
- Кламп self-check: при expectedCount > 0 лишние выдуманные пункты отбрасываются
  (prefix), это чинит занижение и на непустых ответах; при 0 — отдельный промпт
  только про пропущенные поручения (`{"missed": bool}`), supported пуст.
- «Недоступна» остаётся для случая «включено, но сигнал не получен» (парс-провал);
  дефолты новых флагов ConfidenceSignals = true — прямые вызовы reduce в тестах не
  меняют поведение.
- Батч использует тот же пайплайн — унаследует поведение автоматически (код батча
  не правится); python-тулчейн (validate/evaluate) остаётся строгим — расхождение
  зафиксировать в CLAUDE.md модуля.

## Архитектура

- `ActionItemsAnswer.normalizeDegenerateEmpty(_:) -> (text, wasNormalized)` — чистая.
- `ConfidencePrompts`: `selfCheckEmptyPrompt(transcript:)` (только missed; answer не
  нужен — он по определению пустой список);
  `parseSelfCheck(_:expectedCount:)` — кламп к expectedCount; при 0 — items не
  требуются, missed обязателен.
- `ConfidencePipeline`: нормализация primaryText после сборки primary (обе ветки,
  до constraint); нормализация текстов повторов redundancy перед парсом; выбор
  self-check промпта по expectedCount; прокидка флагов enabled в сигналы.
- `ConfidenceSignals` + `formatNormalized: Bool = false`, `redundancyEnabled/
  scoringEnabled/selfCheckEnabled: Bool = true`; `reduce`: formatNormalized →
  worse(.unsure) + причина; «недоступна» — только при enabled && nil.

## Критерии приёмки

1. `{"action_items": []}` при включённом self-check не получает «не подтверждено N из
   N»; missed-вопрос работает (missed=true → UNSURE с причиной).
2. Ответ `{}` → показан нормализованный `{"action_items": []}`, вердикт ≤ UNSURE с
   причиной нормализации, hard-fail «валидный JSON» не срабатывает; повтор `{}` в
   redundancy сравнивается как пустой список (не disagree из-за парса).
3. Выключенный тумблер не порождает причин «…недоступна» (в т.ч. в отчёте эскалации);
   «включено, но сигнал не получен» — причина остаётся.
4. Кламп: self-check с выдуманными лишними пунктами считает не больше expectedCount.
5. `./scripts/build.sh`, `./scripts/test.sh` зелёные; ревью GO.

## Результат

Пустой кейс больше не наказывается: (1) self-check при 0 пунктов задаёт только вопрос
о пропущенных поручениях — «не подтверждено N из N» на пустом списке невозможно по
построению; кламп parseSelfCheck к expectedCount режет выдуманные пункты и на
непустых ответах; (2) вырожденный `{}` нормализуется в `{"action_items": []}` с
предупреждением (UNSURE, не hard-fail) во всех точках — primary обеих веток и повторы
redundancy; (3) «…недоступна» в причинах — только для включённого, но не давшего
сигнала подхода (отчёт эскалации с принудительно выключенными повторами больше не
выглядит сломанным). Осознанное отклонение от строгого python-контракта зафиксировано
в CLAUDE.md модуля; батч наследует поведение через общий пайплайн.

Важно следующим агентам: `normalizeDegenerateEmpty` — только ровно пустой JSON-объект;
дефолты `ConfidenceSignals.*Enabled` = true (прямые вызовы reduce без флагов ведут
себя по-старому); BACKLOG 60 — выбор self-check промпта при непарсибельном primary.
