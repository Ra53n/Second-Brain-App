# Задача 82: сравнение baseline и тюна — слепая оценка, автопроверки, история замеров

## Тип

фича

## Модель

sonnet

## Цель

После дообучения нужно ответить на один вопрос: стало лучше или нет. Сейчас это делается
руками — человек открывает два `.md` рядом, знает, где тюн, и держит счёт в голове.
Пункт «слепое сравнение» из `finetune/criteria.md` на первом прогоне так и не провели
(зафиксировано там же, строка 80), а автопроверки живут в `evaluate.py` и печатают
таблицу в терминал.

Раздел «Тюнинг» получает третий экран: пары ответов бок о бок **без подписей и в
перемешанном порядке**, оценка по осям из `criteria.md`, счёт ведёт приложение и само
говорит, выполнено ли правило приёмки. Рядом — автопроверки по каждому примеру и история
замеров, которая переживает следующий прогон.

## Зависимости

81 (раздел «Тюнинг»: `FineTuneStore`, `FineTuneRunner`, сканер датасетов, поиск
python-окружения — всё переиспользуется).

CLI-тулчейн `finetune/`: `baseline.py` (генерация ответов), `style_checks.py` /
`dictation_checks.py` (пороги и проверки — переносятся в Swift), `criteria.md` обеих
версий (оси слепого сравнения и правило приёмки).

## Объём

1. **Экран «Сравнение»** в разделе «Тюнинг» (`Sources/SecondBrain/FineTune/`): выбор
   датасета, слева baseline, справа тюн, по каждому примеру — вход, два ответа, эталон
   автора, результат автопроверок.

2. **Слепой режим** — ядро задачи. Скрывает подписи, перемешивает порядок внутри каждой
   пары, ведёт по 10 парам подряд. По каждой паре — оценка 1–5 по четырём осям из
   [finetune/criteria.md](../finetune/criteria.md) (строки 44–48): Личный опыт,
   Конкретика, Интонация, Уместность. В конце снимает маску и показывает: тюн выиграл N
   из 10, правило приёмки (`criteria.md:55`, нужно ≥7) выполнено или нет. Незавершённая
   сессия сохраняется и продолжается с того же места.

3. **Автопроверки в Swift** (P1, чистое ядро без I/O) — перенос из python:
   `FineTuneStyleChecks` (8 проверок из [style_checks.py](../finetune/style_checks.py)) и
   `FineTuneDictationChecks` (9 проверок из
   [dictation_checks.py](../finetune/dictation_checks.py)) с их порогами. Итог считается
   как в python: `passed` и `total` только по применимым проверкам (`ok != nil`).
   **Паритет с python пиннится тестом** на закоммиченных артефактах `finetune/baseline/`
   и `finetune/tuned/`: суммы обязаны сойтись с `evaluate.py` — 64/80 baseline и 70/80
   тюн. Разошлись — тест красный, а не «в приложении другие числа».

4. **Чтение артефактов** — `FineTuneOutputsReader`: `outputs.json` в **двух форматах**
   (новый объект с `provider/model/adapter/temperature/results` и старый плоский список
   `[{id, text}]` — оба лежат в репозитории) и `.md`-файлы с **двумя наборами заголовков**
   (`## Вход` в свежих, `## Задание` в закоммиченных). Разбор — чистая функция,
   тестируется на реальных файлах обоих поколений.

5. **Генерация ответов кнопкой**: `baseline.py --data <data> --out <baseline|tuned>
   --count N --temperature T [--adapter <adapters>]` через существующий `FineTuneRunner`.
   Температура и число примеров для тюна берутся **из метаданных снятого baseline**, а не
   из формы: разные параметры делают сравнение нечестным. Процесс регистрируется в
   `BackgroundProcessRegistry` (инвариант №2), как прогон обучения.

6. **История замеров** (P2): `FineTuneEvaluation` в отдельном JSON в Application Support
   рядом с `finetune-runs.json` — дата, датасет, модель, путь адаптера, гиперпараметры
   прогона (из `FineTuneRun`, если замер сделан по нашему прогону), итог автопроверок по
   обеим сторонам, счёт слепого сравнения, вердикт по правилу приёмки. Снисходительный
   декодер, карантин, тест миграции.

7. **Экспорт в `criteria.md`**: кнопка дописывает строку в таблицу замеров репозитория —
   чтобы результат остался в git, а не только в Application Support. Дописывание, не
   перезапись; существующий текст файла не трогается.

## Вне объёма

- **Слепое сравнение для датасета диктовки.** Четыре оси и правило «≥7 из 10» заданы
  только в `finetune/criteria.md` (посты). У диктовки правило приёмки другое
  (`finetune/dictation/criteria.md:69-73`: похожесть, полный зачёт по проверкам), оси
  субъективной оценки там не определены. Для диктовки в этой итерации — автопроверки и
  просмотр пар без слепого режима. **Открытый вопрос:** нужны ли диктовке свои оси —
  спросить владельца перед второй итерацией.
- Правка порогов проверок из UI (пороги — константы, меняются в коде и калибруются
  `calibrate.py`).
- Автоматизация `calibrate.py` и `selftest.py`.
- Редактирование `criteria.md` из приложения сверх дописывания строки замера.
- Облачные провайдеры генерации: в `providers.py` реализация ровно одна (`MLXProvider`),
  тюна в публичных API Anthropic и OpenAI нет — причина зафиксирована в `finetune/README.md`.
- Регистрация обученного адаптера в `FunctionRouter` (остаётся пунктом 42 бэклога).

## Допущения и corner-кейсы

Ответы владельца по развилкам (2026-07-31), дословно по смыслу:

- **Главное на экране — слепое сравнение.** Не просто две колонки с подписями: знание
  «где тюн» смещает суждение, а именно этот пункт `criteria.md` до сих пор не выполнен.
- **Проверки переносятся в Swift**, а не вызываются через `evaluate.py`. Владельцу
  озвучен риск: 17 проверок с порогами будут жить в двух местах и могут разойтись с
  python. Митигация — тест паритета на закоммиченных артефактах (пункт 3 объёма);
  расхождение обязано быть красным тестом.
- **Генерация ответов тюна — кнопкой в приложении**, чтобы петля «взять чекпоинт →
  снять ответы → сравнить» не выходила в терминал.
- **История замеров — свой JSON плюс экспорт в `criteria.md`**, чтобы результат попадал
  в git, а не жил только в Application Support.

Найдено разведкой по коду, учесть при реализации:

- **`finetune/tuned/` в `.gitignore`** (строка 32), как и `adapters/`, `runs/`. В чистом
  клоне правой колонки нет вообще. Для диктовки нет и `tuned/`, и `adapters/` — тюн там
  ещё не запускался.
- **Два формата `outputs.json`.** Новый (объект с метаданными прогона) лежит в
  `finetune/dictation/baseline/`, старый (плоский список) — в `finetune/baseline/` и
  `finetune/tuned/`. У старого нигде не записано, каким адаптером снят тюн.
- **Два поколения `.md`.** В `finetune/baseline/` и `finetune/tuned/` секция называется
  `## Задание` и есть строка `- исходный пост:`; в `finetune/dictation/baseline/` —
  `## Вход` и строка `- провайдер:`. Разделение по `^## ` безопасно: внутри тел ответов
  встречаются `###`, но не `## ` (проверено по всем 30 файлам).
- **Знаменатели сторон могут не совпадать.** Набор применимых проверок зависит от текста
  ответа (например, проверка заглавных возвращает «н/п», если предложений нет), поэтому
  «70/80» у тюна может считаться по своему знаменателю. Показывать долю честно, а не
  подставлять знаменатель baseline, как это делает `evaluate.py:96`.
- **`criteria.md` расходится с пересчётом.** Строка 70 заявляет «Примеров с результатом
  ≥ 7/8: 6 из 10 → 8 из 10», фактический пересчёт на тех же артефактах даёт 4 → 8.
  Аналогично `dictation/criteria.md:55` («6 из 10» против фактических 5). Приложение
  показывает пересчитанное; расхождение с документом — ожидаемое, не баг. Суммы
  64/80 и 70/80 сходятся точно, их и берём как эталон паритета.
- **Набор из 10 примеров — первые 10 строк `valid.jsonl` без всякого seed**
  (`baseline.py:62-63`). В `finetune/data/valid.jsonl` строк 12, поэтому два примера
  (`anons_habr__draft_to_post`, `anons_habr__topic_to_hook`) в замер не попадают и молча
  выпадают в `evaluate.py`. Экран должен показывать, сколько примеров из скольких снято.
- **`--adapter` не резолвится относительно `finetune/`** (в отличие от `--data` и
  `--out`) — путь трактуется от рабочего каталога процесса. `FineTuneRunner` запускает
  CLI с `cwd = finetune/`, значит и адаптер надо передавать относительно него; ошибка в
  пути роняет mlx внутри `load_adapters`, а не на нашей стороне.
- **Генерация требует mlx**, автопроверки — нет. Экран сравнения обязан полностью
  работать без `mlx-lm`: он читает уже снятые ответы. Баннер про окружение — только
  на кнопке генерации.
- **Два одновременных запуска.** Генерация ответов и обучение — разные процессы, но оба
  тяжёлые (пик обучения 11.1 ГБ). Одновременный запуск не блокируем, но предупреждаем,
  как в задаче 81.
- **Прерывание посреди слепой сессии.** Оценки сохраняются по мере ввода; после
  перезапуска сессия продолжается, а не начинается заново — иначе цена ошибки высока
  (десять пар длинных текстов читаются долго).
- **Смена артефактов под открытой сессией.** Если между началом слепой сессии и её концом
  переснять `tuned/`, счёт станет бессмысленным: фиксировать в сессии хэши или mtime
  прочитанных `outputs.json` и предупреждать, что данные изменились.
