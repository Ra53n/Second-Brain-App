# Ключ оценки — агенту не показывать

Что качественное решение обязано **закрыть кодом** или **явно задокументировать как
осознанно отложенное**. Задокументированное с обоснованием ограничение — это нормально;
незамеченный кейс — нет. Разница между «решил не делать» и «не подумал» и есть главное,
что мы измеряем.

Составлено до прогонов, по коду проекта: `Links/WikilinkParser.swift`, `Links/LinkIndex.swift`,
`Vault/VaultFileOperations.swift`, `Editor/EditorViewModel.swift`.

## A. Формы ссылки, которые надо переписать

1. `[[Заметка]]` — простая.
2. `[[Заметка|подпись]]` — alias: меняется **только цель**, подпись пользователя не трогаем.
3. `[[Заметка#Заголовок]]` — якорь сохраняется.
4. `[[Заметка#Заголовок|подпись]]` — и якорь, и подпись.
5. `[[папка/Заметка]]` — ссылка с путём: меняется последний компонент.
6. Несколько ссылок в одной строке и несколько в одном файле.
7. Ссылки внутри самой переименованной заметки (self-reference).

## B. Что трогать НЕЛЬЗЯ

8. `[[Заметка]]` внутри код-блока ``` и inline-кода — `WikilinkParser` их уже игнорирует
   (`testLinksInCodeAreIgnored`); решение обязано переиспользовать парсер, а не резать regex
   по тексту.
9. Совпадение подстроки: `[[Заметка о лете]]` при переименовании `Заметка` — не задето.
10. Ссылки на **другую** заметку с похожим именем (`ЗаметкаBackup`) — ловушка префикса,
    та же, что закрыта в `VaultPath`.
11. Обычный текст «Заметка» вне `[[ ]]`.

## C. Инвариант №1 — массовая правка чужих файлов

12. **Атомарность/всё-или-ничего.** Сбой на 5-м из 20 файлов не оставляет vault наполовину
    переписанным: либо откат, либо явный отчёт «что успели» с возможностью починить.
13. **Согласие пользователя на массовую правку.** Переименование одной заметки правит
    N чужих файлов — это должно быть видно заранее (сколько файлов/ссылок) или отменяемо.
14. **Запись только через `VaultFileOperations`** (или явно обоснованный аналог), не голый
    `FileManager` вразнобой.
15. **Несохранённый буфер редактора.** Если правится файл, открытый в редакторе с
    несохранёнными изменениями, — правка не должна их затереть (`EditorViewModel` уже имеет
    механику конфликта: перечитать / сохранить рядом с суффиксом «(conflict)»).
16. **Внешнее изменение** файла между чтением и записью (Obsidian правит тот же vault).

## D. Corner-кейсы переименования

17. **Коллизия имён** — цель уже существует: `VaultFileOperations.rename` бросает
    `alreadyExists`; ссылки при этом **не должны** быть переписаны (сначала успешный rename,
    потом ссылки — или транзакция).
18. **Rename только регистра** (`заметка` → `Заметка`) на case-insensitive APFS: файл «уже
    существует» сам для себя — классическая ловушка.
19. **Папка, а не файл.** Переименование папки меняет пути всех вложенных заметок; допустимо
    вынести за объём, но заметить обязательно.
20. **Пустое/невалидное имя, расширение** — `validate(name:)` уже есть, не ломать.
21. **Заметка без входящих ссылок** — быстрый путь, ничего не переписываем.
22. **Кириллица, пробелы, эмодзи** в имени; UTF-16-безопасная работа с диапазонами.

## E. Инженерия

23. **Чистое ядро (P1):** «текст файла + старая цель + новая цель → новый текст» — чистая
    функция без ФС, тестируемая таблицей случаев. Не логика внутри ViewModel/View.
24. **Переиспользование:** `WikilinkParser` (диапазоны и правила), `LinkIndex.backlinks(to:)`
    (кто ссылается), `VaultFileOperations.rename`. Свой парсер `[[...]]` — минус.
25. **Индексы после правки:** `LinkIndex` и поисковый индекс должны увидеть изменения
    (существующий `refresh()`/`updateFile`), иначе backlinks врут до перезапуска.
26. **Тесты:** таблицы случаев из A и B, temp-vault для файловых, ноль сети.
27. **Стиль:** русский заголовок файла (что живёт / поток данных / оговорка), `///` на типах,
    комментарии «почему».
28. **UI:** существующий диалог переименования (`VaultViews`, `renameTarget`) переиспользуется,
    не создаётся второй; результат виден пользователю.

## Что считать отличным результатом

Закрыты A и B полностью, C.12–15 закрыты или осознанно ограничены с обоснованием, D.17–18
обработаны, E.23–24 соблюдены, тесты покрывают A/B таблицей. Ограничения перечислены в
`## Результат` файла задачи так, что следующий агент знает, где мины.
