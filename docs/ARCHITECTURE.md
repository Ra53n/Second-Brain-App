# Архитектура Second Brain

Живой документ: агент, меняющий архитектурное решение, обязан обновить этот файл.

## Стек

| Слой | Выбор | Почему |
|---|---|---|
| Язык/UI | Swift 5.9+, SwiftUI (+AppKit для системных вещей) | macOS-only; нативный доступ к аудио, процессам, Keychain; эталонный проект пользователя (Manager Assistant) на том же стеке |
| Сборка | SPM-only executable, без .xcodeproj | Как в Manager Assistant: `swift build` из CLI, `.app` собирает `run.sh` |
| Минимальная ОС | macOS 14+ | Core Audio process tap для записи системного звука (14.4+); MA был на 13 — поднято осознанно |
| Хранилище заметок | Обычные .md файлы на диске (Obsidian-совместимо) | Данные переживут приложение; vault открывается в Obsidian |
| Индексы | SQLite (FTS5 для поиска, таблица векторов для RAG) | Всегда пересоздаваемы из vault; system libsqlite3 без внешних зависимостей |
| Локальный LLM-рантайм | Ollama как управляемый child-процесс | Проверенный паттерн MA (RagOllamaLauncher); API для скачивания моделей, чата, эмбеддингов |
| Локальная транскрипция | WhisperKit (CoreML) | Лучший Whisper на Apple Silicon; работает in-process |
| Облачные провайдеры | OpenAI, Gemini, Deepgram/AssemblyAI | Требование пользователя; за единой абстракцией, добавление новых тривиально |
| Git | Обёртка над git CLI через `Process` | Без libgit2-зависимостей; auth через системный credential helper / SSH |

## Инвариант №1: vault — источник истины

Приложение работает поверх выбранной пользователем папки (возможно, это его живой Obsidian vault). Отсюда:
- никакая операция не должна терять/молча перезаписывать пользовательские файлы;
- все производные данные (FTS-индекс, векторный индекс, кэши) лежат вне vault (`~/Library/Application Support/SecondBrain/<vault-id>/`) и пересоздаваемы;
- доступ к папке — через security-scoped bookmark, переживающий перезапуск.

## Инвариант №2: жизненный цикл фоновых процессов

Любой процесс, запущенный приложением (Ollama, будущие рантаймы):
- регистрируется в `LocalRuntimeManager` (единый владелец PID);
- запускается лениво — при первом запросе к локальной модели;
- гасится по idle-таймауту (настраиваемому; дефолт 10 мин, `IdleShutdownPolicy`);
- **гарантированно** убивается в `applicationWillTerminate`: SIGTERM → grace-период 3 с → SIGKILL выжившим (`BackgroundProcessRegistry.terminateAll`);
- сигнал шлётся группе процесса (killpg), если ребёнок стал её лидером, иначе самому процессу — Foundation.Process не даёт установить process group при spawn (нет POSIX_SPAWN_SETPGROUP), поэтому дерево Ollama гасится через его собственную корректную обработку SIGTERM;
- чужой (не нами запущенный) сервер не гасится никогда — ни по idle, ни при выходе;
- WhisperKit — не процесс, а in-process CoreML-модель (гигабайты RAM): та же `IdleShutdownPolicy` выгружает её из памяти после простоя (`WhisperKitProvider.unloadIfIdle`), кэш моделей — в `Application Support/SecondBrain/WhisperKit` (виден UI управления).

## Ключевые потоки данных

**Запись** (задача 06): дорожки стримятся на диск как AAC-в-CAF (CAF валиден на любом префиксе — kill -9 не теряет записанное; .m4a финализируется только при закрытии), при штатной остановке перепаковываются в `.m4a` без перекодирования; осиротевшие после краша `.caf` подхватывает `AudioFileConverter.recoverOrphans` при следующем запуске. Комбинированный режим «микрофон + система» — **две дорожки в два файла** (`<base>.m4a` + `<base> (система).m4a`), без реалтайм-микса: два clock-домена мешать сложно и рискованно, а транскрипции раздельные дорожки удобнее. Системный звук — Core Audio process tap (macOS 14.4+; на старее — graceful fallback на микрофон). Метаданные записи — sidecar `<base>.json` рядом с аудио (самодостаточность + уезжает с vault при git-синхронизации).

**Встреча** (задача 11): `Audio` пишет .m4a в `<vault>/Meetings/_recordings/` → `Meetings` FSM (`recorded → transcribing → transcribed → summarizing → awaitingTitle → filing → done` + `failed` с ретраем шага; таблица переходов — `MeetingFSM.transitions`, статус прогона поверх этапа — `MeetingRunStatus`; персистентно в Application Support, `persistNow()` после каждого перехода, зависшие `running` → `paused` на старте, resume идемпотентен) → `LLM` роутер: транскрипция — функция `.transcription` (все дорожки записи), summary — `.meetingSummary` (структурный промпт `[TRANSCRIPT]`/`[VAULT_FOLDERS]`/`[USER_RULES]`, ответ с маркерами `TITLE:`/`FOLDER:`/`SUMMARY:`; длинный транскрипт — map-reduce чанками ~24 тыс. символов) → название задано до записи — сразу filing, иначе диалог подтверждения → заметка `<vault>/<папка>/YYYY-MM-DD <название>.md` (frontmatter: дата, длительность, провайдер, ссылки на аудио; summary; транскрипт с таймкодами). Папку от LLM валидируем по дереву vault, фолбэк — `Meetings/YYYY-MM`; правила раскладки пользователя — `MeetingSettings.filingRules`. UI раздела (задача 41): компактная строка записи (кнопка + меню источника + название; дефолт источника — «оба входа», `MeetingSettings.resolvedDefaultSource` с деградацией в микрофон на macOS < 14.4) и нижняя статус-строка в стиле settingsBar чата — чип провайдера транскрипции (`TranscriptionRoutePresenter` поверх FunctionRouter: явное назначение / «Авто (X)» / «нет провайдера», переключение пишет назначение `.transcription`) + переход в Settings → «Встречи»; правила раскладки и полные статусы разрешений живут только в настройках. Текст дорожки для summary-промпта собирается из сегментов транскрипта (`TrackTranscript.promptText`) — метки диаризации «Speaker N:» (Deepgram/AssemblyAI) доходят до саммари.

**RAG** (задача 13): FSEvents (`diskChangeTick` VaultManager, debounce 2 с) сообщает об изменениях → инкрементальный реиндекс ТОЛЬКО изменённых по mtime файлов (чанкинг по заголовкам с путём «H1 > H2» и диапазонами строк; заголовки в код-блоках игнорируются → эмбеддинги батчами по 16 через роутер `.embedding` → SQLite `<vault-id>/rag.sqlite`: чанки и Float32-LE-векторы вместе, коммит per-file транзакцией — прерывание не теряет готовое). Автообновление активно только когда индекс уже построен (первая индексация — явная кнопка: эмбеддинги не бесплатны). Поиск — brute-force косинус по всем векторам (`Vector.topK`, семантика FAISS Flat): для личного vault в тысячи чанков это миллисекунды, sqlite-vec не нужен. Смена модели эмбеддинга детектится тегом «model|dim» в БД → предложение полной переиндексации (векторы несовместимы). Исключения: dot-папки, `Meetings/_recordings/`, не-markdown, пользовательский ignore-список. В чате retriever достаёт top-K чанков → в промпт `[RAG_CONTEXT]` → ответ с цитатами `[[заметка]]` (задача 14).

**Реестр баз знаний** (задача 34): базы RAG — список, а не пара. Встроенные `vault` (индекс RagIndexManager) и `project` (README+docs репозитория, `ProjectDocsIndexService`) плюс произвольные папки с .md (`FolderIndexService`: свой `<folder-id>/folder-rag.sqlite`, ленивый sync по mtime, лимиты 1 МБ/2000 файлов). Модель/стор — `KnowledgeBase`/`KnowledgeBaseStore` (`knowledge-bases.json`, паттерн MCPServerStore; встроенные нельзя удалить — только выключить). Per-чат мультивыбор — `ChatConfiguration.enabledKnowledgeBaseIDs` (миграция из legacy `knowledgeSource` задачи 31 в `init(from:)`; encode ручной, legacy-ключ не пишется). Фасад `KnowledgeBaseManager` — единая точка ретрива: RAG для tool-провайдера — инструмент `rag_search` (ОДИН, с параметром base — enum по именам включённых баз: имена функций OpenAI не переваривают кириллицу, значения enum — переваривают; логика в `RagSearchTool`, чистая), модель сама решает, когда и где искать; источники цепляются к сообщению прямо из execute-замыкания с дедупом. Для провайдера без tools (или при выключенном per-чат `ragAsTool`) — статический `[RAG_CONTEXT]` со слиянием включённых баз (`KnowledgeMerge`: сквозная сортировка по score — эмбеддер один, шкала общая; дедуп; глобальный topK). Спецслучай {vault} идёт старым пайплайном RagRetriever (rewrite/rerank/порог) — поведение дефолтных чатов не менялось. Чип «База» показывает включённые базы с пер-базовыми состояниями (`KnowledgeBaseChipRow`), управление реестром — секция «Базы знаний» вкладки «Инструменты».

**Чат**: история чатов в Application Support (не в vault); системный промпт собирает ChatPromptBuilder (база + `[RAG_CONTEXT]` + `[TOOLS]`).

**FSM-прогон ответа** (задача 35, порт TaskFSM/runStateMachine из MA): per-чат тумблер «Полный проход (FSM)» (`ChatConfiguration.agentModeEnabled`, default выкл = «Один запрос» — прежний путь бит-в-бит). Прогон `planning → execution (пошагово) → validation → answer`: таблица `AgentFSM.transitions` — единственный источник истины, guarded `transitioned(to:)` с precondition; все переходы — в ЧИСТОМ `AgentPhaseReducer` («контекст + текст фазы → новый контекст + сообщение», исчерпывающе тестируем без LLM), оркестратор `ChatViewModel+AgentRun` только гоняет LLM/инструменты и персистит. Гарантия терминального ответа: модель не решает, «закончила» ли она, — код двигает шаги; validation-fail расходует `executionRetries` (2), `REPLAN` — `planRetries` (2), при исчерпании — форс-переход в answer; пустой план деградирует в план из одного шага. Жёсткие гейты кода перед фазой (`normalizeBeforePhase`): проверка без done → назад в execution, выполнение без плана → в planning. Каждая фаза — отдельное сообщение ассистента с тегами `agentState/agentStep/agentTotal` (бейджи в UI); промежуточные этапы фильтруются из окна истории следующих ходов и из `dialogContext`. Инструменты внутри фаз — общий `ToolUseLoop` (провайдер без function calling → фазы без инструментов, не ошибка). Crash-safety как у Meeting FSM: `AgentTaskContext` живёт в Chat (chats.json), `persistNow()` после каждого перехода, зависшие `running` → `paused` на старте, пауза/отмена не коммитит фазу — resume идемпотентно повторяет её; гонки — поколение `agentGen` per-чат (сверка после каждого await). Отложено в бэклог (пп. 23–26): swarm-волны, ASK_USER, router-диспетчер интеръекций, режим «План».

**Пайплайны** (задача 36, эталон — routines MA): конфигурируемые автоматизации «TRIGGER → INPUT → AGENT → OUTPUT». Триггеры: ручной, cron (свой минимальный 5-польный парсер `CronExpression` — `*`, `*/N`, списки, диапазоны, weekday 0/7, vixie-OR день/день-недели; `nextDate` с покомпонентными скачками и горизонтом 4 года), отслеживание новых PR GitHub (`PRWatcher`: поллинг `/pulls?state=open` с ETag/If-None-Match, чистый дифф `PRWatchDiff` — первый опрос baseline без триггеров; токен — Keychain «github-token», без него floor интервала 5 мин из-за лимита 60 req/ч). Движок (`PipelineEngine`) НЕ гоняет LLM сам: FSM-оркестратор 35 неотделим от ChatViewModel, поэтому прогон = перенести toolSelection пайплайна (project tools/MCP/базы знаний/режим/провайдер) в конфигурацию destination-чата (пайплайн — источник истины для своих полей; чат создаётся «Пайплайн: <имя>» при отсутствии) и дождаться awaitable-хуков `runAgentToCompletion`/`runSingleTurnToCompletion` — сообщения этапов и итог появляются в чате как при ручном прогоне; сборка инструментов вынесена в общий `ChatToolAssembly.assembleTooling` (единая точка задач 15/21/34/35/36). Прогоны — `PipelineRun` в `pipeline-runs.json` (кап 200; запись running создаётся ДО вызова LLM, normalize на старте running → error «Прерван рестартом»); overlap guard — Set бегущих пайплайнов + занятость чата (второй запуск → `skippedOverlap`, не очередь). Планировщик — минутный тик (чистая решающая логика `PipelineScheduling` отдельно от Task-цикла, эталон AutoBackup); дедуп слота — по `PipelineRun.scheduledFor`; catch-up при старте: РОВНО один пропущенный слот, запись `missed` всегда, догоняющий прогон — только при `catchUpOnStart`. Фоновые циклы (scheduler, watcher) гасятся по willTerminate (инвариант №2; это Task-циклы, не процессы — BackgroundProcessRegistry не при чём). Мосты инструментов чата подвязываются в `AppModel.wire()` (не в ContentView.onAppear — пайплайн может сработать до первого открытия раздела «Чат»). Вне объёма: webhooks, LaunchAgent (при выключенном приложении триггеры не срабатывают), параллельные прогоны одного пайплайна, sink'и кроме чата.

**Code review** (задача 37, поверх пайплайнов 36): три точки входа — пресет «Code Review» (кнопка в разделе «Пайплайны»: PR-watch + FSM + project tools; `PipelineConfig.preset == .codeReview` ключует движок), слэш-команда `/review <URL | owner/repo#N | local>` в чате, локальный diff — делят один `CodeReviewRunner` (`Pipelines/CodeReview/`). Input = [PR]+[DIFF]+[PROJECT_DOCS]+[TESTS]: diff по GitHub API (Accept `vnd.github.v3.diff`; общий `GitHubClient` задач 36/37 с инжектируемым транспортом) либо `GitClient.diff` для локального; большие диффы (>24k символов) сжимаются map-фазой БЕЗ reduce (по вызову модели на чанк; reduce терял бы `file:line` замечаний); доки — `ProjectToolsProvider.helpContext`; тесты — эвристика по именам (`FooTests.swift` среди tracked-файлов), содержимое агент дочитывает read_file. Прогон — полный FSM с новым `displayText` (короткое видимое сообщение, полный input в `AgentTaskContext.task`; снапшот dialogContext вырезает user-сообщение и по displayText). Маркер вердикта — «ИТОГ РЕВЬЮ: APPROVE|НУЖНЫ ПРАВКИ» (НЕ «ВЕРДИКТ:» — он замаскировал бы parseVerdict validation-фазы FSM); бейдж на итоговом сообщении вычисляется из content. Постинг в PR — write-операция (правило бэклога №16): итоговое сообщение получает маркер `ChatMessage.reviewTarget` (только после `.finished`), кнопка открывает шит-превью с редактируемым текстом; автопост — поле пайплайна `autoPostReviewComment` (default выкл), ошибка автопоста не портит статус прогона. `reviewPostedAt` — персистентная метка «Отправлено ✓». Постраничный files() GitHub API намеренно не реализован — файлы извлекаются из diff. Вне объёма: инлайн-комментарии Review API, GitLab, авто-approve, батчи.

**MCP** (задача 15): серверы — конфиг в стиле Claude Desktop (`mcp-servers.json` в Application Support, импорт поддержан); секреты в env через синтаксис `keychain:<имя>` резолвятся из Keychain при запуске. Транспорт — stdio (JSON-RPC 2.0, построчный фрейминг, протокол 2025-06-18; Jira/Confluence — через `mcp-remote`); процессы серверов регистрируются в `BackgroundProcessRegistry` и умирают вместе с приложением. Tool-use цикл: инструменты включённых per-чат серверов → function calling провайдера (OpenAI и Ollama; Gemini — только конверсия схемы, вызовы в бэклоге) → исполнение через `MCPManager` (ошибки текстом `ERROR:`, модель на них реагирует) → до текстового ответа, лимит 6 итераций (последняя форсирует текст). При включённых инструментах ответ приходит без стриминга.

**Встроенные инструменты проекта** (задачи 21, 25, 39): пользователь выбирает git-репозиторий в настройках (`projectRepoPath`; репо самого проекта, репо vault или произвольная папка), а с задачи 39 каталог можно переопределить per-чат (`ChatConfiguration.projectRootPath`, поповер чипа «Проект»; per-root кэш исполнителей в `ProjectToolsProvider.toolset`) → per-чат тумблер «Инструменты проекта» в меню инструментов → модель получает набор git_branches/git_status/git_log/git_diff/list_files/read_file + файловые операции задачи 39 (см. ниже). `/help` (задача 22) отвечает по документации репозитория: при доступном эмбеддере — RAG-ретрив top-K чанков из `<repo-id>/project-docs.sqlite` (ленивая инкрементальная индексация README+docs при вызове), иначе — фолбэк на полный контекст с бюджетом. Архитектура: протокол `BuiltinTool` (name+description+parameters — для LLM, execute — логика), каждый инструмент — отдельный класс, `ToolRegistry` регистрирует набор, общий `ToolExecutor` (actor) находит тулзу по имени и исполняет; ошибки — текстом `ERROR:` (модель реагирует). Имена без «__» — не пересекаются с qualified-именами MCP (`slug__tool`), маршрутизация вызовов в ChatViewModel по этому признаку. Пути от модели — недоверенный ввод (`SafePath`: нормализация, симлинки, запрет выхода из корня); чтение файлов с капом 64 КБ, бинарники отклоняются. Внешние альтернативы — шаблоны `mcp-server-git` (uvx) и `server-filesystem` (npx) в MCP-настройках.

**Файловые инструменты и слой разрешений** (задача 39): к read-only набору добавлены `search_files` (литеральный поиск по содержимому: капы 200 совпадений/5000 файлов/32 КБ вывода, бинарники и >1 МБ пропускаются), `write_file` (создание/перезапись, кап 256 КБ, атомарная запись), `edit_file` (точечная замена old_string→new_string; неуникальный фрагмент — ошибка с подсказкой replace_all), `delete_file` (в Корзину через `trashItem` — обратимо), `run_command` (zsh -c в корне чата, таймаут ≤600 с, вывод ≤32 КБ, процесс в `BackgroundProcessRegistry`). Vault-safety: перезапись существующего файла разрешена ТОЛЬКО после его полного чтения в этом чате и если mtime не изменился (`FileOpsContext` — actor per-чат: реестр чтений + накопитель применённых изменений; обрезанное чтение не регистрируется). Каждая применённая операция сохраняет unified diff в `ChatMessage.fileChanges` (свой чистый `UnifiedDiff`: LCS + hunks, git не нужен) — отчёт и воспроизводимость в истории. Слой разрешений (аналог permission modes Claude Code, закрывает пп. 10 и 16 бэклога): чистый классификатор `ToolRiskClassifier` даёт риск вызова — safe (чтение/поиск/git-обзор/rag_search/allowlist-команды: swift build/test, git status/log/diff…), write (write_file/edit_file и ВСЕ MCP-вызовы — побочный эффект неизвестен), dangerous (delete_file, произвольные команды, редиректы/подстановки, правка скрытых файлов). Режим per-чат `ChatConfiguration.permissionMode`: «Спрашивать» (approve на write+dangerous, дефолт) / «Авто» (approve только на dangerous — прежнее поведение MCP) / «Авто-опасный» (всё без вопросов). Гейт — в `ChatToolAssembly.assembleTooling` вокруг КАЖДОГО вызова: требуется подтверждение → `ToolApprovalCenter` публикует карточку (детали: diff-превью правки/команда/аргументы) и tool-цикл ждёт решения на CheckedContinuation (провайдерских таймаутов между итерациями нет); кнопки «Разрешить» / «На сессию» (ключ операции в in-memory allowlist до перезапуска; для run_command ключ — нормализованная команда) / «Отклонить» (модель получает `ERROR: пользователь отклонил…` и продолжает). Отмена хода/паузы FSM гасит ожидание через cancellation handler. Лимит итераций одиночного хода с project-инструментами поднят до 10 (сценарий «прочитай 3 файла, поправь один, прогони тесты»); в FSM-фазах остаётся 6. Кнопка «Сделать базой знаний» в поповере «Проект» добавляет каталог чата в реестр задачи 34 и включает rag_search по нему.

**Вкладка «Изменения» в чате** (задача 40): кнопка «Изменения · N» в нижней панели чата заменяет ленту сообщений панелью в стиле Claude Code — (1) все файловые операции агента этого чата карточками с цветными diff'ами (`ChatChangesAggregator` по `ChatMessage.fileChanges`), (2) git-обзор эффективного каталога чата: ветка/upstream/ahead-behind, незакоммиченный diff по файлам (`DiffSplitter` режет вывод `git diff` на секции), отличия текущей ветки от main/master (`diff base...HEAD`, только вне базовой ветки) и коммит/пуш прямо из вкладки (`ChatGitBridge` → `GitClient`, создаётся на вызов). Рендер diff'ов единый (`DiffTextView`: фоновая подсветка строк) для вкладки, карточки approve и блока в сообщении. Чистая логика в `ChatChangesModels.swift`, git-обзор `GitChangesOverview.load` тестируется на temp-репозиториях.

**Тюнинг** (задача 81): раздел поверх готового python-тулчейна `finetune/` (в репозитории, вне SPM-таргета) — экран «Датасет» показывает примеры построчно с дифом «вход → эталон» (переиспользованы `UnifiedDiff` и `DiffTextView` задач 39/40), экран «Прогон» — запуск, живой лог и график train/val loss на Swift Charts с отметкой минимума val loss. Смысл графика: на замеренном прогоне val loss достиг минимума на 50-й итерации из 300 и дальше рос — финальный адаптер переобучен, и в текстовом логе это видно, только если вчитываться. **Решение: контракт с CLI — файлы, а не stdout.** `train.py` не печатает JSON ни в одной подкоманде, машиночитаемы только `<workdir>/runs/run.json` и `runs/train.log`; argv для `mlx_lm.lora` собирает CLI, в Swift не дублируется. **Процесс обучения нам не ребёнок:** `train.py start` спавнит его через `Popen(start_new_session=True)` и сразу выходит, у нас есть только pid — поэтому в `BackgroundProcessRegistry` (инвариант №2) регистрируется `FineTunePidProcess`, обёртка `ManagedProcess` поверх pid (`kill(pid, 0)` / `killpg`), а не `Process`; pid ≤ 1 отвергается конструктором, иначе битый `run.json` превратил бы «Остановить» в `killpg(0, …)` по группе процессов самого приложения. Тюн длится часами, поэтому `applicationShouldTerminate` показывает диалог «Остановить обучение / Оставить работать / Отмена»: второй вариант вызывает `detachFromQuit()` (после него `isRunning == false` и сигналы — no-op, `terminateAll()` прогон пропускает), при следующем старте раздел подхватывает его заново по `run.json`. Лог дочитывается таймером раз в секунду от сохранённого смещения — mlx-lm пишет строку раз в ~11 с, а `start` открывает `train.log` на `"w"`, поэтому разобранные точки loss копируются в свой стор по ходу прогона, иначе следующий запуск сотрёт график предыдущего. Чистое ядро: `FineTuneLogParser` (строка лога → точка; val-шаблон проверяется раньше train, резка и по `\n`, и по `\r` из-за tqdm), `FineTuneCheckpointPicker` (минимум val loss, при ничьей — ранняя итерация), `FineTuneJSONL`. **Дефолт python — не наш дефолт (задача 84):** флаги, где они расходятся, приложение задаёт явно — `baseline.py` по умолчанию берёт `temperature 0.7`, а все закоммиченные снимки сделаны на 0.3, и снимок из UI однажды уже молча перезаписал точку отсчёта. Датасет классификации (третий, «поручения из встречи») ломает сразу два порога `validate.py` — повтор одной короткой метки он считает и дублем, и слишком коротким ответом; оба порога опускает один переключатель на вкладке «Примеры», потому что осмысленного «правильного» числа здесь нет, есть решение «это датасет классификации».

**Чат тюнинга и оценка уверенности** (задача 85): шестая вкладка «Чат» — изолированный от главного чата мини-чат для проверки тюненной модели (свой `TuningChatViewModel` + `finetune-chat.json`; `ChatViewModel` осознанно не переиспользован — 834 строки чужой семантики и молчаливый фоллбэк на облако). Инференс — `mlx_lm.server` с `--adapter-path` как управляемый child (`MlxServerManager` по образцу `OllamaManager`: реестр, idle, generation-guard; смена baseline↔тюн — рестарт одного сервера), поверх него `MlxChatProvider` — OpenAI-совместимый HTTP без ключа, **осознанно мимо `FunctionRouter`**: модель фиксирована предметом сравнения baseline/тюн. Память 16 ГБ закрыта двусторонним guard'ом: активный тюн/baseline блокирует чат, старт тюна гасит сервер. Каждый ответ проходит пайплайн уверенности (`FineTune/Confidence/`, чистое ядро; задача 86 сделала его регулируемым — `ConfidencePipelineConfig`, тумблеры в чате, дефолт «только constraint», выключенная стадия даёт nil-сигнал; батч всегда гонит полный набор): constraint-проверки (порт всех 9 из `actionitem_checks.py`, включая autojunk-эвристику `difflib` — эталоны тестов посчитаны реальным python), scoring и self-check отдельными вызовами (в обученный промпт не встраиваются — не ломать контракт строгого JSON), redundancy ×3 без стриминга; редьюсер сводит сигналы в вердикт OK/UNSURE/FAIL, constraint-фейл обрывает пайплайн без лишних вызовов. Батч-прогон 20 примеров valid (10/5/5) пишет `confidence/{baseline,tuned}.{json,md}` + `summary.md` (коммитятся, как `baseline/`).

**Настройки** (задача 17): объектный граф приложения создаёт `AppModel` (владелец — `SecondBrainApp`, общий для главного окна и SwiftUI-сцены `Settings` — стандартное окно Cmd+, со вкладками: Общие/Провайдеры/Модели/Встречи/Локальные модели/Инструменты/Синхронизация). Вкладка «Инструменты» (задача 27) — единая точка настройки туллинга: репозиторий проекта + каталог встроенных инструментов + MCP-серверы; программный переход на вкладку — `SettingsTabRouter` (pending + нотификация openSettingsTab). Индикация в чате: чипы включённых источников инструментов над полем ввода (модели — чистые билдеры `ToolingStatus.swift`) и карточка-мастер «Ассистент проекта» в пустом чате. «Одиночные» значения (dot-папки, авто-открытие vault, интервал авто-бэкапа, idle-таймаут рантаймов) — в `SettingsStore` (settings.json, паттерн ChatStore, одноразовая миграция из старых UserDefaults-ключей); специализированные сторы (routing.json, mcp-servers.json, meeting_settings.json, Keychain) остаются на месте, а связки «настройка ↔ поведение» держит AppModel (Combine, двусторонние с removeDuplicates). Запись meeting_settings.json — только через `MeetingSettingsStore.update` (load-modify-save): файл редактируют два UI. Ключи провайдеров не отображаются никогда (только статус «задан»); проверка ключа — дешёвый GET списочного эндпоинта, секрет только в заголовке (`KeyVerifier`).

**Git** (задача 16): обёртка над git CLI (`GitClient`, actor с FIFO-очередью — параллельные git портят index.lock; парсеры porcelain v2/log/URL — чистые enum). Ручные commit/push/pull из панели в тулбаре + опциональный авто-бэкап по таймеру (`vault backup: <дата>` — как пользователь делает сейчас; неудачный push не дублирует коммиты — следующий прогон видит ahead>0 и допушивает). Конфликты pull: автоматический merge не удался → `merge --abort` (vault никогда не остаётся полу-смердженным) → пользователь выбирает «принять свои»/«принять удалённые» (`pull -X ours/theirs`) или мержит руками через Finder. Auth: только системный credential helper (osxkeychain) или SSH, интерактивные запросы отключены; токен в URL remote детектится и предлагается к удалению из URL (секрет показывается пользователю, приложение его не хранит). Vault, вложенный в чужой репозиторий, репозиторием не считается — защита от коммита родительского репо.

## Что портируется из Manager Assistant

Полная таблица — в [CONVENTIONS.md](CONVENTIONS.md#что-портировать-из-manager-assistant). Портирование = скопировать файл, переименовать под наш домен, адаптировать, сохранить стиль комментариев и принести тесты.

## Решения, принятые владельцем

- Swift/SwiftUI, а не KMP — macOS-only, системные API важнее знакомого стека.
- Ollama, а не встроенный llama.cpp — меньше своего кода, проверено в MA.
- Провайдер транскрипции по умолчанию не фиксируем: пользователь сравнит OpenAI/Deepgram/AssemblyAI/Gemini на своих встречах (см. задачу 19 — инструмент сравнения).
- Дистрибуция (задача 18): только arm64 (Mac пользователя — Apple Silicon; WhisperKit/Ollama целятся в него); подпись ad-hoc + hardened runtime + entitlement микрофона (ветка Б — Developer ID сертификата в Keychain нет), ветка А (Developer ID + нотаризация) заготовлена в dist.sh и включается автоматически при появлении сертификата. Версия — из git-тега в Info.plist.
