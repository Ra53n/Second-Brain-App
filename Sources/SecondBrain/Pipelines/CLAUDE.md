# Модуль Pipelines — правила

Автоматизации на триггерах: ручной, cron (собственный 5-польный парсер) и PR-watch
GitHub. Каждый пайплайн — конфигурация инструментов, моделей и баз знаний, переносится
в destination-чат и проходит полный FSM как ручной запрос. Детали — см. раздел
«Пайплайны» в [docs/ARCHITECTURE.md](../../docs/ARCHITECTURE.md).

## Что здесь живёт

- `PipelineModels` — доменные типы: `PipelineConfig` (триггер, инструменты, провайдер,
  входной шаблон), `PipelineRun` (прогоны с timestamp, результат, причина завершения),
  `PipelineRunTrigger` (manual, cron, prWatch, internal).
- `PipelineStore` — персистентность конфигов и истории прогонов (`pipelines.json`,
  `pipeline-runs.json` с капсулой ~200 прогонов), `prWatchState` (список уже виденных
  номеров PR).
- `CronExpression` — парсер cron (5 полей: минута/час/день/месяц/день-недели); поддержка
  `*`, `*/N`, списки и диапазоны; 4-летний горизонт для редких слотов; чистая логика
  без таймеров (тестируется мок-датами).
- `PipelineEngine` — оркестратор прогона: управление destination-чатом, overlap guard
  (второй запуск при живом первом → `skippedOverlap`), запись running ДО LLM и
  финализация после, трансфер конфигурации пайплайна в чат.
- `PipelineScheduler` — два слоя: `PipelineScheduling` (чистая логика, какие пайплайны
  due в минуту; catch-up при старте; дедуп по `scheduledFor`) и минутный тик-задача.
- `PRWatcher` — два слоя: `PRWatchDiff` (чистый дифф списков PR; первый опрос — baseline)
  и поллинг-цикл GitHub API с ETag, rate-limit tracking; интервал опроса не может быть
  меньше `PipelineTrigger.minPollIntervalMin` (5 мин, жёсткий пол независимо от наличия
  токена).
- `PipelineViews` — раздел UI с конфигами, историей, кнопкой «Запустить».
- `CodeReview/` — подпапка для пресета code review: `CodeReviewRunner` (общая логика
  ввода diff+доки+тесты), `GitHubClient` (HTTP с инжектируемым транспортом, ETag,
  Bearer), `PRReference`/`CodeReviewInput`/`CodeReviewPrompts` (распарс GitHub, сборка
  инпута, структурный промпт с маркерами вердикта).

## Инварианты

1. **Жизненный цикл фоновых циклов** (инвариант №2 проекта в приложении к пайплайнам):
   `PipelineScheduler` (минутный тик cron) и `PRWatcher` (минутный тик поллинга) —
   Task-циклы (не процессы, `BackgroundProcessRegistry` не при чём). Оба запускаются
   лениво в `AppModel.wire()` и гасятся **гарантированно** в `applicationWillTerminate`.
   Ни `tickTask`, ни `watchTask` не должны остаться зависшими при краше приложения.
2. **Конфигурация пайплайна — источник истины СВОИХ полей в destination-чате:**
   инструменты, базы, режим, провайдер перезаписываются при каждом прогоне. Остальное
   (temperature, historyWindow, ragTopK) не трогаем — пользовательская настройка чата
   перетирает пайплайн.
3. **Запись running создаётся ДО вызова LLM**, финализируется после. Рестарт посреди
   прогона оставляет trace (паттерн P5: persistNow); normalize на старте переводит
   зависшие `running` → ошибка.
4. **Overlap guard: пайплайн не может бежать дважды одновременно.** Второй запуск при
   живом первом фиксируется `skippedOverlap` (не очередь, не wait). Эталон —
   `MeetingPipeline.runningIDs`.
5. **Дедуп cron-слотов: по `PipelineRun.scheduledFor`.** Если слот уже отражен в истории,
   прогон на этот слот пропускается (защита от дублей при рестартах и множественных
   тиках).
6. **Catch-up при старте:** только ОДИН пропущенный слот, запись `missed` всегда
   (факт пропуска не теряем), прогон только если `catchUpOnStart` включён.
7. **Токен GitHub — в Keychain** (запись «github-token»); в UI не показывается, всегда
   читается свежий (пользователь мог обновить в настройках).
8. **Первый опрос PRs — baseline без триггеров:** existing PRs не считаются «новыми»,
   иначе включение пайплайна зальёт чат. `lastSeen == nil` → наполнить, триггеров нет.
9. **Постинг комментария в PR — только с подтверждением пользователя**, кроме явно
   включённого `autoPostReviewComment` (default выкл): кнопка открывает шит-превью с
   редактируемым текстом, `GitHubClient.postComment` не вызывается напрямую из движка
   без этого пути.

## Как тестируем

- `CronExpression` — парсинг валидных/невалидных выражений, matches и nextDate на
  фикстурах дат; все комбинации полей: `*`, диапазоны, списки, `/` (задача 36).
- `PipelineScheduling` — due-пайплайны для минуты, catch-up decision, дедуп слотов;
  мок-даты вместо реальных таймеров.
- `PRWatchDiff` — новые PR vs. lastSeen, baseline, переоткрытия.
- `PipelineEngine` — create destination-chat или вернуть существующий, overlap guard,
  трансфер конфигурации; моки провайдеров (`MockProviders`).
- `CodeReviewRunner` — сборка diff (GitHub API и локальный git), слияние доков и тестов,
  вызов LLM с displayText, вердикт по маркеру.
- Персистентность — миграция при добавлении нового поля в `PipelineConfig` (старый
  JSON без него грузится; тест обязателен).
- Новое нод в `CodeReview/` — не тестируем сквозной вызов GitHubClient в тестах,
  моксим транспорт.

## Частые ошибки прошлых задач

- **Пайплайн запускается дважды в одну минуту.** Причина: не хватает дедупа по
  `scheduledFor` в истории, либо сама дата конфликтует. Проверь `PipelineRun.scheduledFor`
  перед записью run'а.
- **Первый опрос PR-пайплайна зальёт чат триггерами на все существующие PR.** Защита:
  `PRWatchDiff.newPRs` с `lastSeen == nil` возвращает baseline без триггеров.
- **Стоп при включённом пайплайне среди ночи.** Причина: при старте после перерыва не
  считается пропущенный слот (отсутствует catch-up decision или он выключен), шаг
  пропускается без логирования. Проверь логику планировщика и флаг `catchUpOnStart`.
- **Фоновые циклы не гасятся при завершении приложения.** Task'и остаются в памяти.
  Обязателен вызов `stop()` для `PipelineScheduler` и `PRWatcher` в
  `applicationWillTerminate` (инвариант №2).

## Куда не лезть

- Саму работу с чатом (создание, запрос агента) — модуль `Chat/` и `AgentFSM/`.
- Провайдеров LLM и роутинг — `LLM/`.
- Постинг комментария в PR реализован (`GitHubClient.postComment`), но не как свободная
  write-операция: только через подтверждение пользователя (шит-превью, маркер
  `ChatMessage.reviewTarget`) либо явно включённый `autoPostReviewComment` на пайплайне
  (default выкл, `CodeReviewRunner.postStartComment`/`autoPostIfConfigured`,
  `PipelineEngine` вызывает автопост строго после успешного терминала). Новых способов
  постить в GitHub мимо этого пути не добавлять без пересмотра решения.
- Инлайн-комментарии Review API, GitLab, авто-approve, батчи — вне объёма (см. раздел
  «Code review» в `docs/ARCHITECTURE.md`).
- Пользовательские источники данных (папки, проекты) — модуль `RAG/` и `Vault/`.
