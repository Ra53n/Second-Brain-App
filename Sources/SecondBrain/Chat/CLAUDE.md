# Модуль Chat — правила

Чаты, персистентность истории, промпты, сборка инструментов, FSM-прогон ответа,
вкладка «Изменения». Самый нагруженный модуль проекта — правила здесь строже.

## Что здесь живёт

- `ChatViewModel` — владелец состояния раздела; всё, что мутирует чат, проходит через него.
- `ChatModels` / `ChatStore` — доменные типы и персистентность (`chats.json`).
- `ChatPromptBuilder` — системный промпт: база + `[RAG_CONTEXT]` + `[TOOLS]`.
- `ChatToolAssembly` — **единственная** точка сборки набора инструментов (встроенные,
  MCP, базы знаний) и гейт разрешений вокруг каждого вызова.
- `AgentFSM/` — прогон `planning → execution → validation → answer`: чистый
  `AgentPhaseReducer` + оркестратор `ChatViewModel+AgentRun`.
- `ChatChangesModels` / `ChatChangesView` — вкладка изменений: diff'ы агента + git-обзор.
- `ToolApprovalCenter` — карточки подтверждения, ожидание решения на `CheckedContinuation`.

## Инварианты

1. **Переходы состояний FSM — только в `AgentPhaseReducer`**, через `ctx.transitioned(to:)`.
   Оркестратор гоняет LLM и персистит, но не решает, куда идти. Новое поведение фазы —
   это правка редьюсера и тест в `AgentReducerTests`, а не `if` в оркестраторе.
2. **Гарантия терминального ответа.** Модель не решает, закончила ли она: бюджеты
   `executionRetries` (2) и `planRetries` (2), при исчерпании — форс-переход в `answer`.
   Не добавляй путей, где прогон может зациклиться или молча остановиться.
3. **Гонки — через поколение.** После КАЖДОГО `await` в оркестраторе сверяй `agentGen`
   с текущим: пользователь мог отменить ход, сменить чат или запустить пайплайн.
4. **Crash-safety.** `persistNow()` после каждого перехода; на старте `running` → `paused`;
   resume идемпотентен — повтор незакоммиченной фазы обязан быть безопасным.
5. **Инструменты собираются только в `ChatToolAssembly.assembleTooling`** — это общая
   точка задач 15/21/34/35/36. Пайплайны, слэш-команды и code review ходят туда же.
6. Промежуточные сообщения фаз (`agentState`/`agentStep`/`agentTotal`) фильтруются из окна
   истории следующих ходов и из `dialogContext` — иначе модель видит свои черновики.
7. Лимиты итераций tool-цикла: **10** для одиночного хода с project-инструментами, **6**
   внутри фаз FSM. Меняешь — объясняй в задаче, почему.

## Как тестируем

- Чистый редьюсер — исчерпывающе, без LLM: `AgentReducerTests`, `AgentFSMTests`.
- Оркестрация — на моках провайдеров (`MockProviders`), `AgentOrchestratorTests`.
- Подтверждения — `ApprovalFlowTests`; вкладка изменений — `ChatChangesTests`.
- Новое поле в `Chat`/`ChatConfiguration` ⇒ тест миграции: старый JSON без него грузится.
- UI (`ChatViews`, 1200 строк) не тестируем — проверяется смоуком через `/smoke-ui`.

## Частые ошибки прошлых задач

- Настройки чата уходят в тулбар или поповер. **Нет**: per-chat настройки живут в нижней
  статус-строке (`settingsBar`, стиль Claude Code) — это осознанное решение владельца.
- Логика правится в оркестраторе, потому что «так быстрее» — редьюсер перестаёт быть
  источником истины, тесты продолжают быть зелёными, поведение расходится.
- Забытая сверка поколения после `await` → сообщения прошлого прогона всплывают в новом чате.

## Куда не лезть

Retrieval и базы знаний — модуль `RAG/`; сами инструменты — `Tools/`; протоколы
провайдеров и роутинг — `LLM/`. Здесь только их сборка и вызов.
